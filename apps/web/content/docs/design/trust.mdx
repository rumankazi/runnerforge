RunnerForge runs your GitHub Actions jobs on VMs in our Google Cloud project. To do that, it needs a GitHub App installation on your repositories. This page lists exactly what that installation lets us do, what we keep, and where it falls short, so you can decide whether to install it.

The code is the source of truth. If this page disagrees with it, the page is wrong. Please open an issue.

## Where things stand

- **The App is private today,** so only the owner can install it. An installation gets VMs only once the owner approves it in the tenant registry, and then only within its limits, unless the owner lifts them. The owner's own installation is on the allow-list (`ALLOWED_INSTALLATION_IDS`): admitted unlimited, without a registry read. An installation is one GitHub user or organization, and RunnerForge treats each one as a tenant. Personal accounts and organizations are both supported.
- **Planned:** a free hosted beta on RunnerForge's GCP project, with manual approval through the tenant registry and [per-installation limits](/docs/guides/limits#per-installation-limits). Running the whole backend yourself is also planned for later. Neither has a date, and there is no paid tier.

## What the App can access

The orchestrator requires these permissions. An installation token without them fails validation (`models.py`):

| Permission | Level | Why |
|---|---|---|
| Actions | Read | To receive `workflow_job` webhooks, and to read a job's status when reconciling its record |
| Administration | Read & write | To create runner registration tokens for your repository, to check whether one of our runners is still busy, and to remove an idle runner of ours before its VM is deleted |
| Metadata | Read | GitHub grants this to every App |

The App needs the **Workflow job** event. The orchestrator acts on `workflow_job` deliveries (runners) and on the `installation` events GitHub sends every App, which keep your installation's registry row current. It acknowledges any other event and ignores it.

<Callout type="warn" title="Administration: write is a powerful permission">
  GitHub only issues registration tokens for repository-level self-hosted runners to callers with `Administration: write`. That permission isn't limited to runners. It's GitHub's repository-administration permission, which also covers changing repository settings, managing collaborators and branch protection, and deleting the repository. RunnerForge's code calls only the endpoints listed below, but the permission itself would let a compromised App do much more on the repositories you install it on. Weigh that before installing, and limit the installation to the repositories that need runners.
</Callout>

## Every GitHub API call RunnerForge makes

All of them are in [`github_client.py`](https://github.com/rumankazi/runnerforge/blob/main/apps/orchestrator/src/runnerforge/github_client.py):

| Call | When | Why |
|---|---|---|
| `POST /app/installations/{installation_id}/access_tokens` | For each queued job that passes our checks; during the daily cleanup sweep (at most once per installation, only if it needs to check a runner); and every 5 minutes in the reconciler (at most once per installation, only if one of its job records is due a check or waiting for a runner, or one of its VMs needs a runner check) | Gets a short-lived installation token |
| `POST /repos/{owner}/{repo}/actions/runners/registration-token` | For each queued job that passes our checks; and in the reconciler, for each job it starts under your installation's limits (at most 10 a run; at most 2 starts per job, plus up to 3 retries after a zone or quota capacity error) | Gets a token the new VM uses to register itself as a runner for that repository |
| `GET /repos/{owner}/{repo}/actions/runners?name={vm_name}` | Daily sweep, only for a VM that is between 1 hour and 6h15m old; and every 5 minutes in the reconciler, for a VM over 15 minutes old (at most 10 a run) | Checks whether the runner on a still-running VM is busy, so an idle or finished VM can be deleted |
| `DELETE /repos/{owner}/{repo}/actions/runners/{runner_id}` | Reconciler, only for a runner of ours that GitHub lists as idle, with no job of yours it could take, right before its VM is deleted | Removes the runner's registration, so GitHub can't hand it one of your jobs while its VM shuts down |
| `GET /app/installations` | Reconciler, once an hour (as the App, with its JWT; paginated) | Lists every installation of the App, to keep the tenant registry current if an `installation` webhook was lost |
| `GET /app/installations/{installation_id}` | Reconciler, once an hour, only for an installation missing from that list; and every 5 minutes for an installation whose row says it was suspended or uninstalled (at most 10 a run) | Confirms with GitHub that it was really uninstalled or suspended before acting on it |
| `GET /repos/{owner}/{repo}/actions/jobs/{job_id}` | Reconciler, every 5 minutes, for job records that are open and due a check (at most 25 a run, with backoff up to 6 hours per job), and for jobs waiting for a free slot under your limits (at most 3 per free slot a run) | Reads the job's status, conclusion and runner, to fill in what the webhooks missed, and to check a waiting job still needs a runner before starting one |

There are no other calls. In particular, the orchestrator never reads repository contents, pull requests, issues or workflow files through the API. Your installation settings show the exact permissions the App holds.

## Your job runs on our machines

The API boundaries above don't cover the VM itself. Your job runs on a VM in RunnerForge's GCP project, so everything the job handles is on that VM: checked-out source, build outputs, and any secrets or `GITHUB_TOKEN` your workflow passes to it. Anyone with admin access to the RunnerForge GCP project could reach that VM and its disks while it exists. Any hosted runner works this way. Only send workflows to RunnerForge whose code and secrets you're comfortable running on our infrastructure.

What limits exposure:

- **One VM per job.** Each queued job gets its own fresh VM, which registers as an ephemeral runner (`--ephemeral`) and accepts one job only.
- **VMs are deleted.** The VM is deleted when GitHub reports its job completed. The reconciler deletes VMs whose runner finished or never got a job, every 5 minutes, and a daily sweep backs that up, and GCE deletes every VM after at most 6h15m of runtime, even if RunnerForge is down. Both disks are deleted with the VM.
- **No external IP.** Runner VMs have no public IP address, so they can't be reached from the internet. They reach it outbound through Cloud NAT.

## What we store, and where

Everything below lives in the GCP project `runnerforge`. Cloud Run and the runner VMs run in `europe-west4` (VMs in zone `europe-west4-a`). Logs and traces use Cloud Logging and Cloud Trace with their default storage location and retention settings, which Terraform doesn't change.

**On each VM, deleted with the VM:**

- **Name:** `runnerforge-{run_id}-{job_id}-{run_attempt}`.
- **Labels** (also on its disks): `runner`, `job_id`, `run_id`, `run_attempt`, `repository_id` (the numeric GitHub ID), `installation_id`, `webhook_trace_id`, `webhook_span_id` and `queued_received_at`.
- **Metadata:** `registration-token` (the runner registration token, readable from inside the VM until it's deleted), `repo-url` (`https://github.com/{owner}/{repo}`), `runner-labels` (your job's `runs-on` labels) and `startup-script`.

**In Firestore, one record per job, kept for 90 days:**

The database `runnerforge` is in `europe-west4`. It holds a record only for jobs from approved installations ([ADR-018](/docs/design/decisions#per-job-state-in-firestore-behind-a-jobstore-protocol)), keyed `{run_id}-{job_id}-{run_attempt}`:

- **Identity:** `installation_id`, `repository_id`, `repo` (`owner/name`), `run_id`, `job_id`, `run_attempt` and your job's labels.
- **What happened:** the decision (VM submitted, duplicate, label rejection with its reason and the offending labels, or a rejection or deferral under your approval or limits with its reason), the VM creation outcome, the runner name, the job's conclusion, a preemption, or the step that failed and its error class. Each with a timestamp.
- **Retention:** a TTL policy deletes each record after 90 days, usually within a day of expiry. After you uninstall the App, the reconciler deletes all of your installation's records within a few runs (5 minutes apart) of your VMs being gone. Point-in-time recovery keeps 7 days of earlier versions, deleted records included.

**In Firestore, one row per installation (the tenant registry):**

When you install the App, GitHub tells RunnerForge, and the database `runnerforge` gets a row for the installation ([ADR-019](/docs/design/decisions#tenant-registry-install-to-register-admin-approval-per-installation-limits)). It holds the installation ID, your account's ID, login and type (user or organization), the approval state (`pending` until approved), its limits, the last 20 approval, suspension and limit decisions with their times, GitHub's status for the installation (active, suspended or uninstalled), and timestamps. After you uninstall the App, a TTL policy deletes the row 30 days later.

No tokens are stored there.

**In Cloud Logging:**

- The orchestrator's log lines for a RunnerForge job carry `repo`, `owner`, `sender` (the GitHub login that triggered the job), `job_id`, `run_id`, `run_attempt`, `runner_name`, `runner_id` and `installation_id`. Some lines also include your job's labels and timing values (`logger.py`, `main.py`, `handlers.py`).
- `installation` events (install, uninstall, suspend, unsuspend) are logged with the action and the installation ID (`admission.py`), whether or not the installation is approved.
- Request logs record the request URL, the caller's IP and the user agent, which for webhooks are GitHub's.
- If a webhook payload or GitHub response doesn't match the expected shape, the values that failed validation are logged. For a missing field, that value can be the enclosing object, up to the whole payload.
- The VM's system logs are shipped by the Cloud Ops Agent. They include the startup script's output, which names the repository URL. Anything else written to the VM's system logs during the job ends up there too.

**In Cloud Trace:** every request is traced. Spans carry `repo`, `sender`, `job_id`, `installation_id`, `labels`, `run_id`, `run_attempt`, `runner_name` and the VM's labels. The automatic HTTP instrumentation also records the outgoing GitHub API URLs, which contain the repository name and job ID.

**Not stored:** installation tokens and the App JWT are kept in memory only and never written anywhere. Valid webhook payloads aren't logged in full.

## Isolation today

<Callout type="warn" title="Tenants share one project">
  All installations' VMs run in the same GCP project, zone and VPC network (`default`). Each job gets its own VM, but RunnerForge doesn't configure firewall rules to separate one tenant's VMs from another's on that network. Per-tenant isolation is planned and doesn't exist yet.
</Callout>

Other tenant-level controls that exist today:

- **Admission.** Only installations the owner has approved in the tenant registry can create VMs, plus the allow-listed owner's installation. Other installations get no VM, but their webhooks are still acknowledged.
- **Per-installation limits.** Each approved installation is capped on concurrent VMs, machine size and runtime unless the owner lifts its limits ([Limits](/docs/guides/limits#per-installation-limits)), so one tenant can't take the whole shared pool.
- **Deletion ownership.** A "job completed" event can delete a VM only if that VM's own labels say RunnerForge created it for the same installation that sent the event. One tenant's events can't delete another tenant's runner.

## What limits the damage if RunnerForge is compromised

- **Repository scoping.** You choose which repositories the installation covers. An attacker with full control of RunnerForge could act only on those repositories, but on each of them with the full `Administration: write` permission described above.
- **Short-lived GitHub tokens.** Installation tokens and registration tokens each expire after 1 hour (GitHub sets both lifetimes). The App's private key is the only long-lived credential. It's stored in GCP Secret Manager and mounted into the orchestrator as a file. It isn't in source control or Terraform state.
- **You can cut access at any time.** Suspending or uninstalling the App on your account or organization stops RunnerForge from getting new tokens for it. Within about 5 minutes the reconciler deletes your idle VMs; one still running a job is deleted 15 minutes after a suspension, or at once after an uninstall. Their runners stay listed as offline in your repository settings, because RunnerForge can no longer remove them. Logs and traces aren't erased; they expire on their own retention.
- **Signed webhooks.** The orchestrator rejects any webhook that isn't signed with the App's webhook secret, so a forged request can't create VMs.

If the App's private key leaks, the maintainer can generate a new key and delete the old one in the App settings. You don't need to do anything. Key rotation is manual today.

More detail on the implementation is in [Security](/docs/design/security).

## How you can check

1. **Your installation settings** show exactly which permissions and repositories the App has. These are the limits GitHub enforces, whatever this page says.
2. **The source code.** Every GitHub API call is in `github_client.py`, and every VM label and metadata key is set in `handlers.py`.
3. **Your repository's runner list.** While a job runs, its runner, named `runnerforge-…`, appears under **Settings → Actions → Runners** and then disappears.
4. **Try a test repository first.** Install the App on a throwaway repository before granting it anything that matters.

## Known limitations

- **Administration is broader than we need.** It's the only permission GitHub accepts for repository-level runner registration.
- **Tenants aren't isolated** at the project or network level yet. See [Isolation today](#isolation-today).
- **Limits are soft.** A burst of jobs queued at once can start more VMs than an installation's concurrency limit, and every tenant shares the project's quotas.
- **No certification or third-party audit.** This is a portfolio platform-engineering project, not a commercial service. You can check the claims here against the public source code, but no third party has attested them.
- **No bug bounty.** Please report security issues privately to the maintainer, not in a public issue.
