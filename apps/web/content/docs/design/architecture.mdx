RunnerForge has two layers. An **infrastructure layer** (Terraform, Packer) changes rarely and is applied
through CI. A **per-job layer** (the orchestrator) reacts to every `workflow_job` webhook by creating or
deleting one VM.

```text
GitHub ──workflow_job──▶ Cloud Run: orchestrator ──insert/delete──▶ GCE runner VMs (europe-west4-a)
   ▲                         │  ▲                                        │
   │   registration token ◀──┘  └── POST /sweep (daily), /reconcile (5 min) │
   └──────────────── runner registers itself, runs one job ◀── Cloud NAT ┘
```

## Components

### GitHub App

The App is **private** today. Each installation (one GitHub user or organization) is a tenant. The
orchestrator acts on `workflow_job` events, and on `installation` events, which keep the tenant registry
current. GitHub also sends `ping` and similar events, which the orchestrator acknowledges and ignores.

Minimum permissions, checked on every installation token the orchestrator mints (`models.Permissions`;
a token without them fails validation):

| Permission | Used for |
| --- | --- |
| Actions: read | `workflow_job` webhooks; `GET /repos/{repo}/actions/jobs/{id}` in the reconciler |
| Administration: read & write | `POST /repos/{repo}/actions/runners/registration-token`; `GET /repos/{repo}/actions/runners?name=` in the sweep and the reconciler; `DELETE /repos/{repo}/actions/runners/{id}` in the reconciler's orphan cleanup |
| Metadata: read | Required by GitHub for repository access; not called directly |

Why Administration is needed, and what bounds it, is on [Trust & threat model](/docs/design/trust).

### Orchestrator (Cloud Run)

A FastAPI service, `runnerforge-orchestrator`, in `europe-west4` (`infra/terraform/cloud_run.tf`):

- **Scaling:** 0 to 50 instances, up to 10 concurrent requests each, with 1 vCPU and 512 MiB.
- **Ingress:** public (`allUsers` invoker), because GitHub posts from many IPs. Each route does its own auth.
- **Routes:**
  - `POST /webhook` checks the HMAC signature. See [Webhook flow](/docs/design/webhook-flow).
  - `POST /sweep` accepts only a Cloud Scheduler OIDC token for the expected service account and audience.
  - `POST /reconcile` accepts the same token as `/sweep`. See [Webhook flow → Reconciler](/docs/design/webhook-flow#reconciler).
  - `GET /health` is a liveness probe.
- **Modules:** `handlers.py` (per-action logic), `machine_policy.py` (labels → machine type),
  `github_client.py` (App JWT → installation token → registration token), `compute_client.py` (GCE),
  `sweep.py`, `reconcile.py` (job records, ADR-018), `job_store.py`, `admission.py` and `registry.py`
  (tenant registry and limits, ADR-019), `security.py`.
- **Deploys:** on each orchestrator release, `deploy-orchestrator.yaml` builds the image and signs it with
  Cosign. It starts a new revision on 5% traffic, then ramps to 100% after approval.

<Callout type="warn" title="Env var changes ship with the next release">
  Terraform owns the service's env vars, but production traffic is pinned to the revision CD deployed.
  A revision created by `terraform apply` gets no traffic. A changed env var, such as `admission` or a new
  entry in `allowed_installation_ids`, takes effect with the next orchestrator release.
</Callout>

### Admission

`ADMISSION` (from the Terraform variable `admission`) selects how installations are admitted
([ADR-019](/docs/design/decisions#tenant-registry-install-to-register-admin-approval-per-installation-limits)). Production admits by the tenant registry (`ADMISSION=registry`):

- Installations in `ALLOWED_INSTALLATION_IDS` (from `allowed_installation_ids`; only the owner's) are
  admitted, unlimited, with no registry read. An unset or empty list means none skips the registry.
- Every other installation needs an approved row in the tenant registry (the `installations` collection
  of the Firestore database `runnerforge`) and gets that row's limits. Installing the App creates a
  `pending` row; the owner approves, suspends and sets limits with `runnerforge-admin`
  ([Approving tenants](/docs/guides/runbooks/tenants)).

With `ADMISSION=allowlist`, the default for a self-hosted install without a registry,
`ALLOWED_INSTALLATION_IDS` alone decides, with no limits:

- **Unset:** every installation is allowed. This is meant for self-hosting, and it logs a startup warning.
- **Empty string** (an empty Terraform list): nobody is allowed. This works as a kill switch.
- **Comma-separated IDs:** only those installations are allowed.

A malformed ID or an unknown mode makes the new revision fail at startup, so it never takes traffic.
Only `queued` events are gated. `in_progress` and `completed` always pass, so VMs of a removed installation
are still cleaned up.

### Runner VMs

A runner VM is **ephemeral**: the runner registers with `--ephemeral`, runs one job and exits. The VM is
never reused. **Spot** is a separate choice that controls how the VM is billed. A job opts in with the
`spot` label. Spot VMs are cheaper but GCE can reclaim them mid-job. For a failed or cancelled job, the
orchestrator checks the audit log and logs `Job ended due to spot preemption` if GCE reclaimed the VM.

Every VM (`compute_client.create_vm`):

- **Location:** zone `europe-west4-a`, on the `default` network.
- **Networking:** no external IP. Egress goes through Cloud NAT (`runnerforge-nat`, auto-allocated IPs;
  `network.tf`, ADR-009).
- **Disks:** a 10 GB boot disk from the runner image, and a 50 GB `pd-balanced` data disk mounted at
  `/home/runner/actions-runner/_work`. Both auto-delete with the VM.
- **Runtime cap:** GCE deletes the VM after 6 h 15 min of running (`max_run_duration`, termination action
  `DELETE`). That is GitHub's default 6 h job timeout plus 15 min for boot.
- **Service account:** `runnerforge-runner-vm`, which has only `roles/logging.logWriter`.
- **Labels** (copied onto both disks for cost attribution): `runner=runnerforge`, `job_id`, `run_id`,
  `run_attempt`, `repository_id`, `installation_id`, `queued_received_at`, and the queued webhook's
  trace and span IDs.
- **Metadata:** `registration-token`, `repo-url`, `runner-labels`, `startup-script`.

The startup script (`runnerforge/scripts/startup_script.sh` in the orchestrator package) mounts the data
disk, reads the metadata, and registers the runner under the VM's own name. That is why a `completed` event's `runner_name` names the VM to delete.

### Runner image

Packer (`infra/packer/`) builds on Debian 12. It bakes in the GitHub Actions runner (version pinned in
`infra/packer/scripts/install-runner.sh`), its dependencies, Docker, and the Cloud Ops Agent.
`deploy-runner-image.yaml` builds the image, smoke-tests it on a real VM, and promotes it into the `runnerforge-runner` image
family. It then deprecates
everything older than the five newest images, with deletion after 30 days. A rollback deprecates the bad
image, and the family falls back to the next newest.

**Pinning:** each orchestrator instance resolves the family to a concrete image once, at startup
(`init_runner_image`), and creates every VM from that image. So a newly promoted image is used only by
orchestrator instances that start after it: after a deploy, a scale-out, or a scale from zero. If the
lookup fails, VMs boot from the family alias. The image lives in `RUNNER_IMAGE_PROJECT`, which defaults to
`GCP_PROJECT_ID`.

### Terraform

A single root module in `infra/terraform/` with a GCS backend. Pull requests get a plan (tfaction) and OPA
policy checks (`infra/policies/`). On merge to `main`, `deploy-infra.yaml` applies after approval in the
`prod-infra` environment. A daily drift check (`drift-detection.yaml`) opens issues.
Terraform covers Cloud Run, Cloud Scheduler, NAT, IAM, Workload Identity Federation for CI, secrets, observability (metrics, dashboard, SLOs, alerts), quota preferences (`quotas.tf`), and the Firestore job store: database, TTL field and indexes (`firestore.tf`).

## Identities

| Service account | Roles | Why |
| --- | --- | --- |
| Orchestrator | `compute.instanceAdmin.v1`, `compute.imageUser` | Create and delete VMs from the runner image |
| | `iam.serviceAccountUser` on the runner VM SA | Attach that SA to the VMs it creates |
| | `secretmanager.secretAccessor` on two secrets | Read the webhook secret and the App private key |
| | `logging.logWriter`, `logging.viewer`, `cloudtrace.agent` | Write logs and traces; read audit logs for the preemption check |
| | `datastore.user`, conditioned on the `runnerforge` Firestore database | Read and write job records (ADR-018) |
| `runnerforge-runner-vm` | `logging.logWriter` | Ship VM logs. Nothing else. |
| `runnerforge-scheduler` | none (signs OIDC tokens) | Identity that `/sweep` and `/reconcile` accept |

These are the runtime identities (`iam.tf`, `runner_vm.tf`, `scheduler.tf`, `firestore.tf`). CI authenticates through
Workload Identity Federation with its own service accounts (`wif.tf`, `runner_image.tf`, `terraform_ci.tf`).

## What changes when

| Layer | Owns | Changes | Tool |
| --- | --- | --- | --- |
| Infrastructure | Cloud Run service, IAM, NAT, scheduler, observability, quotas, Firestore job store | On merge, after approval | Terraform via CI |
| Image | Runner binary, Docker, OS packages | On a `runner-image` release | Packer via CI |
| Per job | One VM per queued job, deleted on completion | Every webhook | Orchestrator |

## Cost when idle

With no jobs, no runner VM is running and no CPU is billed. Cloud Scheduler calls `/reconcile` every 5
minutes, so one Cloud Run instance usually stays warm, but with request-based billing and
`min_instance_count = 0` only the time spent handling requests is billed (an empty run takes about a second,
well inside Cloud Run's free tier). What remains is mostly storage (runner images, container images, logs,
secrets, Terraform state, job records) plus any fixed charges of the supporting services, such as Cloud NAT.
Cloud Run over GKE was chosen for this (ADR-001 in [Decisions](/docs/design/decisions)).

## Where this is going

These are planned, not built:

- **Free hosted beta.** RunnerForge runs the VMs in its own GCP project. Installations join by manual
  approval in the tenant registry and get per-installation limits. Both are already in place; opening the
  beta means making the App public.
- **Self-hosting.** Run the whole backend (orchestrator, image, infrastructure) in your own GCP project. The
  `allowlist` admission default with an unset allow-list, and the separate `RUNNER_IMAGE_PROJECT`, already
  lean this way.

Bring-your-own GCP project for the hosted service and paid billing are deferred.
