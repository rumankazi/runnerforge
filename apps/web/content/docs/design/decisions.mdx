## Cloud Run over GKE for the orchestrator

### Context

The orchestrator needs to receive HTTP webhooks, process them, and call external APIs (GitHub, GCE). Traffic is bursty and unpredictable — long idle periods followed by bursts when developers push code.

### Options considered

- **GKE Autopilot** — managed Kubernetes with pay-per-pod pricing. Familiar ecosystem, but the control plane alone costs ~$72/month regardless of usage.
- **Cloud Run** — fully managed, scales to zero, pay-per-request. No cluster to manage.
- **Always-on VM** — a single small VM running the FastAPI app. Simple, but always costs money even when idle.

### Decision

Cloud Run. The zero-idle-cost model is the deciding factor for a portfolio project with sporadic usage. The orchestrator's workload (receive webhook, make a few API calls, return) is a natural fit for request-based serverless compute.

### Consequences

- True zero cost when idle.
- Each webhook request runs in an isolated container — no shared state, no race conditions.
- Cold start adds ~1 second to the first request after idle, which is acceptable given the overall 35-second VM boot time.
- Cannot run long-lived background processes. The orphan cleanup sweep is handled via Cloud Scheduler triggering a separate endpoint, not an in-process loop.

## GCE VMs over Kubernetes pods for runners

### Context

Runners need to execute arbitrary CI/CD workflows, which often include Docker builds, service containers, and potentially untrusted code.

### Options considered

- **Kubernetes pods on GKE** — fast startup (2–5 seconds), but Docker-in-Docker is messy and has security implications. Pods on the same node share a kernel. GKE also requires the ~$72/month control plane.
- **GCE VMs** — full isolation (separate kernel per runner), Docker runs natively, but boot time is 30–45 seconds with a pre-baked image.
- **Firecracker/gVisor** — micro-VM or sandboxed container runtimes. Strong isolation with near-container speed, but significantly more complex to set up and operate.

### Decision

GCE VMs with Packer-built images. Full isolation without kernel sharing, native Docker support, and zero idle cost (VMs only exist during job execution).

### Consequences

- 30–45 second boot time vs 2–5 seconds for pods. Acceptable for the current use case.
- No GKE control plane cost.
- Docker runs natively — no Docker-in-Docker hacks needed.
- Each VM is fully isolated. A malicious workflow cannot affect other jobs.
- VM lifecycle management (creation, label tracking, deletion, orphan cleanup) is our responsibility.

## Python (FastAPI) over Rust or Go for the orchestrator

### Context

The orchestrator is an API choreography service — it receives webhooks, calls GitHub and GCE APIs, and returns. It is not compute-bound.

### Options considered

- **Rust** — excellent performance and memory safety, but a steep learning curve (borrow checker, async runtimes). Would consume weeks of the project timeline on language mechanics rather than platform engineering concepts.
- **Go** — strong concurrency model, popular in platform tooling. Viable choice, but adds a new language to the learning scope.
- **Python (FastAPI)** — already known, mature Kubernetes and GCP client libraries, async support, automatic OpenAPI documentation.

### Decision

Python with FastAPI. The project's value is in the platform engineering architecture, not the implementation language. Python lets us focus on the orchestration patterns, and it is the language most commonly found in platform tooling.

### Consequences

- Faster development — no time spent learning a new language.
- FastAPI provides automatic OpenAPI docs, which is good for portfolio presentation.
- Target roles expect Python fluency for platform tooling.
- If performance ever becomes a bottleneck (unlikely for this workload), the orchestrator could be rewritten in Go without changing the architecture.

## GCE VM labels over a database for state tracking

### Context

The orchestrator needs to track which VMs belong to which jobs, so it can clean them up on `completed`/`failed` webhooks and identify orphans during sweep.

### Options considered

- **Firestore or Cloud SQL** — a dedicated database storing job-to-VM mappings. Full query flexibility, but adds infrastructure, cost, and a write in the critical webhook path.
- **Redis / Memorystore** — fast in-memory store. Always-on cost, and data is lost on restart.
- **GCE VM labels and metadata** — attach `job_id`, `repo`, and `runner=runnerforge` as labels directly on the VM. Query via the GCE API's label filter.

### Decision

GCE VM labels. The VMs themselves are the source of truth. On `completed`: find VM with matching `job_id` label, delete it. On sweep: list all VMs with `runner=runnerforge`, check creation timestamps and job status.

### Consequences

- No database infrastructure to provision, manage, or pay for.
- The Cloud Run orchestrator stays completely stateless — no writes to worry about in the critical path.
- Query performance is fine for the expected scale (tens of VMs, not thousands).
- At production scale with thousands of concurrent runners, this approach would need to be revisited — GCE API list calls aren't designed for high-frequency querying. A lightweight store (Firestore) would make sense at that point.

## On-demand provisioning over warm pools

### Context

Runner startup latency is ~35 seconds with a Packer image. A warm pool of pre-booted runners could reduce this to near-zero, but at the cost of always-on infrastructure.

### Options considered

- **On-demand** — create a VM only when a `queued` webhook arrives. 35-second latency, zero idle cost.
- **Warm pool** — maintain a minimum number of pre-booted, pre-registered runners per label set. Near-instant job assignment, but ongoing cost even when no jobs are running.
- **Hybrid** — warm pool for common labels, on-demand for rare ones.

### Decision

On-demand only for the initial build (Phases 1–4). The 35-second latency is well within the ≤ 1 minute requirement, and zero idle cost is a hard constraint for the project.

### Consequences

- Every job waits ~35 seconds for a runner. Acceptable for the current scope.
- Zero cost when no jobs are running.
- The architecture supports adding warm pools later (Phase 5) without structural changes — the warm pool manager would simply pre-create VMs using the same Compute client module.

## Structured logging over Firestore for initial observability

### Context

We need observability from day one to understand boot times, failure rates, and system behavior. The question is where to store this data.

### Options considered

- **Firestore from day one** — write a document per job with timing data. Full query flexibility for dashboards immediately.
- **Structured JSON logs to Cloud Logging** — log structured data from the FastAPI app. Cloud Run automatically sends stdout to Cloud Logging. Use log-based metrics for dashboards.
- **Both** — structured logs plus Firestore writes.

### Decision

Structured logging only for Phases 1–3. Add Firestore in Phase 4 when building user-facing dashboards.

### Consequences

- Zero additional infrastructure for observability in the early phases.
- Every step is timed and logged: `signature_validated_ms`, `token_fetched_ms`, `vm_created_ms`.
- Cloud Monitoring can create dashboards from log-based metrics without any database.
- No database write in the critical webhook path — keeps the handler fast and simple.
- Firestore is added later as a convenience layer for user-facing queries, not as the source of truth.

## Workload Identity Federation over service account keys for CI auth

### Context

- CI workflows (qualify, build, deploy, terraform apply) need to authenticate to GCP - push images to AR (Artifact Registry), deploy Cloud Run, modify IAM/Secret Manager, manage state bucket.
- Need a credential mechanism that lets GH Actions act on GCP resources without storing portable secrets

### Options considered

- **Long-lived SA JSON keys in GH Secrets** - store a downloaded SA key as a GH Actions secret, `gcloud auth activate-service-account --key-file`. Simple to set up; familiar pattern.
- **Workload Identity Federation** (chosen) — GCP trusts GitHub's OIDC issuer; workflows exchange a short-lived OIDC token for a federated identity that impersonates a target SA
- **Cloud Build with GitHub trigger** — Cloud Build watches the repo; auth is implicit because builds run on GCP-side infra. Means qualify and build/deploy live in different systems.

### Decision

- WIF with two SAs from day one: ci-build (eventual: AR write + Cloud Run deploy) and ci-terraform (broader: state bucket + IAM + Secret Manager + scheduler).
- Pool `github-actions`, provider `github`, attribute condition pinned to `repository == rumankazi/runnerforge && ref == refs/heads/main`.
- For 2.1, both SAs hold only `roles/viewer`. Permissions widen per phase as workflows are added.
- No `google_service_account_key` resource exists anywhere in TF.

### Consequences

- **Pro**: no portable secret exists. Even a logged credential config file is useless without a fresh, validly-signed GitHub OIDC token. Tokens are ~1hr; OIDC tokens that originate them are ~10min.
- **Pro**: every token exchange logged in Cloud Audit Logs (sts.googleapis.com); full traceability of which workflow run impersonated which SA.
- **Pro**: rotation eliminated. There's nothing to rotate.
- **Trade-off**: GCP-side setup is more involved (pool, provider, condition, bindings) than dropping a JSON key in GH Secrets. One-time cost.
- **Trade-off**: locked into GitHub Actions as the OIDC issuer. Moving CI providers means re-doing the WIF pool/provider/conditions for the new issuer.
- **Trade-off**: WIF auth assumes a green path through several layers (token issuance, attribute condition match, IAM binding, target API enabled). When it fails, the error often points at one layer while the cause is in another (we hit this with cloudresourcemanager.googleapis.com being disabled).

## Scale-to-zero orchestrator with skip-fast on non-runnerforge webhooks

### Context

- The orchestrator is a GitHub App that subscribes to the `workflow_job` event. GitHub Apps deliver **all** subscribed events to a single webhook URL — no event-level filtering by label, no per-org/per-repo routing.
- `workflow_job` fires for **every** job in any repo where the App is installed, including jobs that target GitHub-hosted runners (no `runnerforge` label). The orchestrator's label-check happens inside the handler — by the time we know we don't care, Cloud Run has already woken up.
- This produces a steady trickle of irrelevant wakeups during developer work, each costing a ~3-5s cold start when the service had scaled to zero.

### Options considered

- **Scale-to-zero + skip-fast** (chosen) — `min_instance_count=0`, HMAC verify, parse, label check, return 200 immediately for irrelevant events. Cold start on first wakeup per idle period; warm window (~15min) covers subsequent calls.
- **Always-warm** — `min_instance_count=1`, no cold start ever. ~$5/mo flat for compute time mostly spent doing nothing.
- **External pre-filter** — Cloud Function or API Gateway in front of Cloud Run, doing a cheap "is this a runnerforge job?" check before forwarding. Extra service to maintain; the actual orchestrator still needs to wake up for real work; same end result.
- **GitHub App event filtering** — would solve this cleanly. Doesn't exist.

### Decision

- Scale-to-zero with skip-fast. Accept the cold-start cost on irrelevant wakeups in exchange for $0 compute during idle periods (nights, weekends, between developer bursts).
- Real runnerforge events benefit from the side effect: an irrelevant wakeup pre-warms the instance, so a real event arriving moments later lands on a hot container.
- The label-check sequence in the webhook handler is: HMAC verify → JSON parse → Pydantic parse → label check → return 200 if no match. Returns to GitHub within ~1s wall-clock on a warm instance, well under the 10s webhook timeout even after a cold start (~3-5s startup + ~1s processing = ~5s p99).

### Consequences

- **Pro**: $0 compute when dormant. For a developer-driven workload that clusters during work hours and goes idle overnight/weekends, this is meaningfully cheaper than always-warm.
- **Pro**: irrelevant wakeups effectively pre-warm the instance for clustered work — first real event after the first irrelevant one runs on a warm container.
- **Pro**: simpler architecture than the pre-filter alternative. No extra service to deploy, monitor, or upgrade.
- **Trade-off**: a fraction of CPU/cost goes to handling events we discard. At our volume, sub-penny per day; acceptable.
- **Trade-off**: cold-start latency on the first real runnerforge event after an idle period (3-5s + handler time). Still well under the GitHub webhook 10s budget; orchestrator p99 has comfortable headroom.
- **Future micro-optimization**: a byte-scan for `b"runnerforge"` on the raw request body before Pydantic parse would shave 5-15ms per irrelevant event. Not worth implementing until volume of irrelevant events justifies it — Cloud Run startup dominates the cost, not Pydantic.

## Self-observed VM provisioning with NAT-based egress

### Context

- Burst test (2026-06-09): 18 jobs across 6 workflow runs in a ~20s window. The orchestrator handled all 18 webhooks correctly and logged `Submitted VM creation` for each.
- But ~10 of 18 VMs failed silently during GCE provisioning with `QUOTA_EXCEEDED` on `IN_USE_ADDRESSES` (default external-IP quota is 8/region in europe-west4; each VM was claiming one via `ONE_TO_ONE_NAT`).
- The orchestrator was unaware: the fire-and-forget pattern submits an insert, gets an operation handle, logs the submission, and walks away. The operation's actual outcome (DONE / failure / quota-exceeded) is never checked.
- Diagnosis required cross-system log correlation: orchestrator logs + GCE audit logs + GitHub workflow status. Operational visibility was poor.

Two coupled problems surfaced: a GCE-side quota constraint AND missing self-observability in the orchestrator.

### Options considered

**For visibility into VM creation outcomes**:

- **Sweep-only detection** (status quo, extended): hourly poll of GCE state to find failed operations and orphan VMs. Cheap; detection latency up to 60 min — slower than the GitHub 10-min job timeout.
- **Synchronous polling in webhook handler**: `await operation.result()` inside the handler. Blocks the webhook for 30-60s, blowing GitHub's 10s webhook delivery budget. Rejected.
- **Background polling with sync client + `asyncio.to_thread`**: each poll occupies an OS thread for 30-60s. The default ThreadPoolExecutor caps at ~5 workers on 1 vCPU. At concurrency=10 the pool starves. Rejected.
- **Background polling with async compute client + FastAPI `BackgroundTasks`** (chosen): coroutine-based polling on the event loop. Each task is ~5-50KB of state (vs 8MB per thread). Webhook returns immediately; the watcher runs alongside, polling GCE and emitting structured outcome events.
- **Cloud Tasks / Pub-Sub worker queue**: the "right cloud-native" pattern for async work, but vast overkill at one-operator scale. Reserved for any future SaaS-scale move.
- **Retry / self-healing in the orchestrator**: explicitly rejected. Retry doesn't help with the failure mode we actually see (quota doesn't free up within the GitHub 10-min job timeout). Retry only helps with rare random transients (~0.1% of GCE provisions); the engineering cost (state tracking, retry counters, backoff, tests) far exceeds the benefit at our scale.

**For the underlying quota constraint**:

- **Per-VM external IPs** (status quo): each VM claims one external IP via `access_configs ONE_TO_ONE_NAT`. Bounded by region's `IN_USE_ADDRESSES` quota.
- **Cloud NAT egress** (chosen): one shared NAT gateway provides outbound connectivity for all runner VMs. VMs become private-only. Self-hosted GH runners only need outbound (poll GitHub for jobs); inbound connectivity is unnecessary. Removes the quota constraint entirely.
- **Quota increase request only**: temporary fix; doesn't change the architecture and still leaves us bounded by whatever new ceiling we negotiate.

### Decision

- Migrate `_compute_client` from `compute_v1.InstancesClient` (sync, bridged via `asyncio.to_thread`) to `compute_v1.InstancesAsyncClient` (native asyncio). Drops the thread-bridge in `compute_client.py`.
- Webhook handler schedules a `BackgroundTasks` watcher per VM creation: `await operation.result(timeout=120)`. On terminal state, the watcher logs a structured outcome event (`vm_creation_succeeded` or `vm_creation_failed` with `error_class`/`error_message`).
- New log-based metric `vm_creation_outcome_count` labeled by `outcome={success,failure,timeout}` → alert on failure rate > 5%.
- Sweep stays as a backup safety net for edge cases (deploy-time rolling restart, OOM, manual termination — all of which can interrupt in-flight background tasks).
- Provision Cloud NAT in `infra/terraform/`: `google_compute_router` + `google_compute_router_nat` in europe-west4. Remove `access_configs` from VM `network_interfaces` in `compute_client.py`. All VM egress (GitHub API, Artifact Registry) routes through the NAT gateway.

### Consequences

- **Pro — operational visibility**: every VM creation outcome is captured in structured logs. Failure rate becomes a metric, alertable, queryable. Root-cause analysis no longer requires cross-system log correlation.
- **Pro — detection latency**: drops from up to 60 minutes (sweep) to ~60 seconds (background polling). Stays well inside the GitHub 10-minute job timeout.
- **Pro — quota removed**: Cloud NAT eliminates `IN_USE_ADDRESSES` as a constraint on VM provisioning. The burst that caused this incident would succeed in full under the new architecture.
- **Pro — coroutine economics**: async client + `BackgroundTasks` scales easily. At concurrency=10, total background-task memory cost is ~500KB. Thread-based polling would have cost ~80MB and saturated the executor.
- **Pro — Cloud NAT cost is trivial**: ~$1.40/month per gateway + a small per-GB processing fee. Negligible at our scale.
- **Trade-off — VMs lose inbound connectivity**: acceptable because self-hosted GH runners are outbound-only. We have no use case for inbound.
- **Trade-off — edge-case visibility loss**: background tasks interrupted by deploy / OOM / manual termination won't emit their outcome event. Sweep remains the catcher for these rare cases. Acceptable.
- **Trade-off — request concurrency ceiling unchanged**: container memory (512 MB) still caps in-flight webhook requests around ~25 (each holds ~10-20 MB of state). Background tasks are cheap; webhook requests are not. Raising `max_instance_request_concurrency` beyond ~30 doesn't deliver real capacity gain — the bottleneck is downstream APIs (GitHub installation token rate limit, GCE INSTANCES quota), not our threading model.
- **Trade-off — no auto-recovery**: we observe but don't retry. If GCE rejects a VM creation, the corresponding GitHub job times out at the 10-minute mark. Acceptable because the failure modes we see (quota, code bugs) wouldn't benefit from retry. If we ever see meaningful transient-failure patterns, revisit.
