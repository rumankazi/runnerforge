## Cloud Run over GKE for the orchestrator

### Context

The orchestrator needs to receive HTTP webhooks, process them, and call external APIs (GitHub, GCE). Traffic is bursty and unpredictable: long idle periods followed by bursts when developers push code.

### Options considered

- **GKE Autopilot**: managed Kubernetes with pay-per-pod pricing. Familiar ecosystem, but a cluster carries a management fee on top of the pods, whether or not anything runs.
- **Cloud Run**: fully managed, scales to zero, pay-per-request. No cluster to manage.
- **Always-on VM**: a single small VM running the FastAPI app. Simple, but always costs money even when idle.

### Decision

Cloud Run. The zero-idle-cost model is the deciding factor for sporadic usage. The orchestrator's workload (receive webhook, make a few API calls, return) fits request-based serverless compute.

### Consequences

- Zero compute cost when idle (`min_instance_count = 0` in `infra/terraform/cloud_run.tf`; see [ADR-008](#scale-to-zero-orchestrator-with-skip-fast-on-non-runnerforge-webhooks) for the cold-start trade-off).
- Instances are **not** one-request-per-container. `max_instance_request_concurrency = 10`, so up to 10 webhooks share one Python process, and the service scales between 0 and 50 instances. What a process holds is limited to API clients and startup caches (the GCE machine-type list and the pinned runner image, see [ADR-013](#runner-image-pinned-at-startup-with-deprecate-then-delete-retention)). No job state lives in the process, so any instance can handle any event.
- No long-lived background loops. Work that must outlive a request is either a FastAPI `BackgroundTasks` job tied to that request (the VM-creation watcher and the preemption cross-check) or the `/sweep` endpoint, which Cloud Scheduler calls once a day (`12 0 * * *` UTC in `infra/terraform/scheduler.tf`).

## GCE VMs over Kubernetes pods for runners

### Context

Runners need to execute arbitrary CI/CD workflows, which often include Docker builds, service containers, and potentially untrusted code.

### Options considered

- **Kubernetes pods on GKE**: pods start in seconds, but Docker-in-Docker is messy and has security implications. Pods on the same node share a kernel. GKE also adds a cluster to pay for and operate.
- **GCE VMs**: a separate kernel per runner, Docker runs natively, but boot takes tens of seconds even with a pre-baked image.
- **Firecracker/gVisor**: micro-VM or sandboxed container runtimes. Strong isolation with near-container speed, but much more complex to set up and operate.

### Decision

GCE VMs booted from a Packer-built image (`infra/packer/`). One VM per job: the runner registers with `--ephemeral`, so it takes exactly one job and exits.

### Consequences

- Boot-to-ready is slower than a pod (about 35 seconds with the pre-baked image, measured in Phase 1).
- No GKE cluster to pay for or operate.
- Docker runs natively. No Docker-in-Docker.
- Each job gets its own kernel and disks. VMs still share the project's `default` network and the `runnerforge-runner-vm` service account (which holds only `roles/logging.logWriter`), so isolation is per-VM, not per-network.
- VM lifecycle (creation, labels, deletion, orphan cleanup) is our code's job. See [ADR-004](#gce-vm-labels-over-a-database-for-state-tracking) and [ADR-014](#gce-enforced-runtime-cap-with-delete).

## Python (FastAPI) over Rust or Go for the orchestrator

### Context

The orchestrator is an API choreography service: it receives webhooks, calls GitHub and GCE APIs, and returns. It is not compute-bound.

### Options considered

- **Rust**: excellent performance and memory safety, but a steep learning curve (borrow checker, async runtimes). It would spend weeks on language mechanics rather than platform engineering.
- **Go**: strong concurrency model, popular in platform tooling. Viable, but adds a new language to learn.
- **Python (FastAPI)**: already known, mature GCP client libraries, async support, automatic OpenAPI docs.

### Decision

Python with FastAPI. The value is in the orchestration design, not the implementation language.

### Consequences

- Faster development.
- FastAPI generates OpenAPI docs for the routes.
- `google-cloud-compute` ships only a synchronous client, so every GCE call is wrapped in `asyncio.to_thread` to keep the event loop free (see [ADR-009](#self-observed-vm-provisioning-with-nat-based-egress)).
- If performance ever becomes a bottleneck (unlikely for this workload), the orchestrator could be rewritten in Go without changing the architecture.

## GCE VM labels over a database for state tracking

<Callout type="info" title="Revisions">
  **2026-10-27** (orchestrator 0.17.4 and 0.17.5): the original text said the `completed` path finds the VM by its `job_id` label and that VMs carry a `repo` label. Neither is true any more. The `completed` path deletes the VM named in the payload's `runner_name`, and only after an ownership check. The `repo` label was replaced by the numeric `repository_id`, and the sweep reads the exact `owner/repo` from the `repo-url` metadata key.

  **2026-10-28**: [ADR-018](#per-job-state-in-firestore-behind-a-jobstore-protocol) adds a per-job store for job history and status. This ADR still decides VM lifecycle: labels and metadata remain the authority for which VMs exist, who owns them, and what the delete paths and the sweep act on. Once ADR-018's database exists, the consequence "No database to provision, manage, or pay for" no longer holds; the orchestrator process itself stays stateless.
</Callout>

### Context

The orchestrator needs to know which VMs belong to which jobs, so it can delete them when a job finishes and find orphans during the sweep.

### Options considered

- **Firestore or Cloud SQL**: a dedicated database storing job-to-VM mappings. Full query flexibility, but adds infrastructure, cost, and a write in the critical webhook path.
- **Redis / Memorystore**: fast in-memory store. Always-on cost, and data is lost on restart.
- **GCE VM labels and metadata**: store the job's identity on the VM itself and query with the GCE API's label filter.

### Decision

The VMs are the source of truth. `handle_queued` (`handlers.py`) names each VM `runnerforge-<run_id>-<job_id>-<run_attempt>`, and the startup script registers the runner under that same name.

| Where | Key | Holds |
|---|---|---|
| Label | `runner` | Always `runnerforge`. The sweep's list filter. |
| Label | `job_id`, `run_id`, `run_attempt` | Which job the VM was created for. |
| Label | `repository_id` | Numeric GitHub repo id. Always a valid label value, unlike `owner/repo`. |
| Label | `installation_id` | The GitHub App installation (the tenant, see [ADR-016](#multi-tenancy-scope-installation-as-tenant)). |
| Label | `webhook_trace_id`, `webhook_span_id`, `queued_received_at` | Trace anchor and timestamp for [ADR-012](#opentelemetry-traces-exported-to-cloud-trace) and the readiness metric. |
| Metadata | `repo-url` | `https://github.com/<owner>/<repo>`. Labels can't hold it: label values are lowercase-only and at most 63 characters. |

Boot and data disks carry the same labels as the instance (since 0.17.8), so disk cost can be attributed to a job and installation.

How each path finds its VM:

- **`in_progress`**: list by `job_id` + `run_id` + `run_attempt` labels, read the trace anchor and `queued_received_at`.
- **`completed`**: take `runner_name` from the payload. Skip unless it starts with `runnerforge-`. Fetch that VM's labels (`compute_client.get_vm_labels_by_name`). Delete only if `runner == runnerforge` and `installation_id` equals the event's installation; otherwise log `Refusing to delete VM not owned by this installation`. A missing VM is a no-op.
- **Sweep**: list `labels.runner=runnerforge`, read `owner/repo` from `repo-url`. Ask GitHub whether the runner on the VM (same name) is busy: busy → skip, idle or de-registered → delete. If the repo can't be read, or GitHub returns 404, skip rather than guess; the hard age limit still applies.

### Consequences

- No database to provision, manage, or pay for. The orchestrator stays stateless.
- `runner_name` is chosen by whoever registered the runner, so the name prefix proves nothing on its own. The label check is what stops one installation's `completed` event from deleting another installation's VM.
- Labels are not authentication: anyone with `compute.instances.setLabels` in the project could forge them. Today that means the project's owners, the orchestrator SA, and the CI SAs that hold `roles/compute.instanceAdmin.v1` or `roles/editor` (`ci-runner-image-build`, `ci-terraform-apply`).
- Fine at tens of VMs. GCE list calls aren't built for high-frequency querying at thousands of concurrent runners; revisit the store if scale gets there.

## On-demand provisioning over warm pools

### Context

A warm pool of pre-booted runners could make runner pickup near-instant, at the cost of always-on infrastructure.

### Options considered

- **On-demand**: create a VM only when a `queued` webhook arrives. Boot latency on every job, zero idle cost.
- **Warm pool**: keep pre-booted, pre-registered runners per label set. Near-instant pickup, but ongoing cost even when nothing runs.
- **Hybrid**: warm pool for common labels, on-demand for rare ones.

### Decision

On-demand only. Zero idle cost is a hard constraint, and boot latency fits within the Time-to-Register SLO (99.5% of runners ready in under 300 s per calendar month, `infra/terraform/observability_slos.tf`).

### Consequences

- Every job waits for a VM to boot and register.
- Zero cost when no jobs are running.
- A warm pool could be added later without structural changes: it would pre-create VMs through the same `compute_client` module. Not currently planned.

## Structured logging over Firestore for initial observability

<Callout type="info" title="Revisions">
  **2026-10-27**: the original text promised Firestore "in Phase 4" for user-facing dashboards and listed log fields (`signature_validated_ms`, `token_fetched_ms`, `vm_created_ms`) that the orchestrator never emitted. Both were removed. Tracing is covered separately in [ADR-012](#opentelemetry-traces-exported-to-cloud-trace).

  **2026-10-28**: [ADR-018](#per-job-state-in-firestore-behind-a-jobstore-protocol) adds a Firestore job store for product reads (dashboard, tenant registry). This ADR still holds for observability: log lines and log-based metrics remain the source for metrics, SLOs and alerts. The consequence "no database write in the critical webhook path" no longer holds once ADR-018's writes ship: each write is bounded by a timeout and fails open.
</Callout>

### Context

We need to understand boot times, failure rates, and system behavior from day one. The question is where that data lives.

### Options considered

- **Firestore**: write a document per job with timing data. Full query flexibility.
- **Structured JSON logs to Cloud Logging**: Cloud Run sends stdout to Cloud Logging; dashboards come from log-based metrics.
- **Both**.

### Decision

Structured JSON logs only (`logger.py`). Every metric is a log-based metric. All but one match a fixed orchestrator log message (`jsonPayload.message`) and extract fields from it; `vm_preemption_count` reads the GCE audit log (`compute.instances.preempted`) instead. Examples:

| Log message | Metric (`observability_metrics.tf`) |
|---|---|
| `Submitted VM creation` | `vm_creation_count` |
| `VM creation outcome` | `vm_creation_outcome_count` (by `outcome`, `machine_type`, `image_version`, `error_code`, `spot`) |
| `Runner registration outcome` | `runner_readiness_seconds` (the Time-to-Register SLO source) |
| `Webhook event received` | `webhook_event_count` |
| `Sweep completed` | `sweep_checked_count`, `sweep_deleted_count`, `sweep_error_count` |

The full surface (18 log-based metrics, 2 SLOs, 8 alert policies, the dashboard) is Terraform-managed in `infra/terraform/observability_*.tf`.

### Consequences

- No observability infrastructure beyond what GCP provides.
- No database write in the critical webhook path.
- Log message strings are an API: renaming one silently breaks its metric. Change them together with `observability_metrics.tf`.
- If a user-facing dashboard needs per-job queries that logs can't answer cheaply, revisit with a new ADR.

## Workload Identity Federation over service account keys for CI auth

### Context

CI workflows need to act on GCP: push images to Artifact Registry, deploy Cloud Run, build runner images, and run Terraform (state bucket, IAM, Secret Manager). We need a credential that lets GitHub Actions do this without storing a portable secret.

### Options considered

- **Long-lived SA JSON keys in GitHub Secrets**: simple and familiar.
- **Workload Identity Federation** (chosen): GCP trusts GitHub's OIDC issuer; a workflow exchanges a short-lived OIDC token for a federated identity that impersonates a target SA.
- **Cloud Build with a GitHub trigger**: auth is implicit, but qualify and deploy would live in different systems.

### Decision

- Pool `github`, provider `github` (`infra/terraform/wif.tf`). The provider's attribute condition requires `repository_owner == 'rumankazi'` and `repository == 'rumankazi/runnerforge'`.
- One SA per job, each bound to a single workflow file through `attribute.workflow_path`:

| SA | Who can impersonate it |
|---|---|
| `ci-build` | `deploy-orchestrator.yaml` |
| `ci-terraform-apply` | `deploy-infra.yaml` |
| `ci-runner-image-build` | `deploy-runner-image.yaml` |
| `ci-terraform-plan` (plan only: `roles/viewer`, `roles/iam.securityReviewer`, `roles/storage.objectUser` on the state bucket) | any workflow in the repo |

- No `google_service_account_key` resource exists anywhere in Terraform.

### Consequences

- **Pro**: no portable secret exists. A leaked credential config is useless without a fresh, validly signed GitHub OIDC token.
- **Pro**: nothing to rotate.
- **Trade-off**: more GCP-side setup (pool, provider, condition, bindings) than a JSON key. One-time cost.
- **Trade-off**: locked to GitHub Actions as the OIDC issuer.
- **Trade-off**: when WIF fails, the error often points at one layer while the cause is in another (we hit this with `cloudresourcemanager.googleapis.com` disabled).
- **Trade-off**: the apply SA can't grant itself a new class of permission in the same apply (for example creating custom roles needed `roles/iam.roleAdmin`). Such grants are bootstrapped out-of-band, then codified in `terraform_ci.tf`.

## Scale-to-zero orchestrator with skip-fast on non-runnerforge webhooks

### Context

- The orchestrator is a GitHub App subscribed to `workflow_job`. GitHub delivers every subscribed event to one webhook URL, with no filtering by label or repo.
- `workflow_job` fires for **every** job in every repo where the App is installed, including jobs for GitHub-hosted runners. GitHub also sends `ping` and installation events whether or not they are subscribed.
- By the time the orchestrator knows an event is irrelevant, Cloud Run has already woken up. When the service was at zero, that costs a cold start.

### Options considered

- **Scale-to-zero + skip-fast** (chosen): `min_instance_count = 0`, and the handler returns 200 as early as possible for irrelevant events.
- **Always-warm**: `min_instance_count = 1`, no cold starts, flat cost for an instance that mostly idles.
- **External pre-filter**: a function in front of Cloud Run. Another service to run; the orchestrator still wakes for real work.
- **GitHub App event filtering**: would solve this cleanly. Doesn't exist.

### Decision

Scale-to-zero with skip-fast. The `/webhook` handler in `main.py` runs, in order:

1. HMAC signature check (401 on failure).
2. Dispatch on the `X-GitHub-Event` header: anything other than `workflow_job` gets 200 and is ignored.
3. JSON and Pydantic parse.
4. Label check: return 200 unless `runs-on` contains `runnerforge` (case-insensitive).
5. Admission check for `queued` events ([ADR-015](#installation-allow-list-as-a-stop-gap-admission-control)).
6. Log `Webhook event received`, then dispatch to the `queued` / `in_progress` / `completed` handler.

### Consequences

- **Pro**: zero compute cost while dormant (nights, weekends).
- **Pro**: an irrelevant wakeup pre-warms the instance for a real event arriving shortly after.
- **Pro**: no extra service to deploy or monitor.
- **Trade-off**: some compute goes to events we discard.
- **Trade-off**: the first real event after an idle period pays a cold start, which has to fit inside GitHub's 10-second webhook timeout. `startup_cpu_boost` is on (`cloud_run.tf`), and the `Cold-start latency p95 > 30s (5m)` alert watches startup latency.
- **Trade-off**: ignored events return before `Webhook event received`, so they don't count in `webhook_event_count` or the lost-webhook ratio. They still appear in the `POST /webhook` access log (`webhook_request_count`) and as `Ignoring GitHub event` or `Skipping! Not a RunnerForge request` log lines.

## Self-observed VM provisioning with NAT-based egress

<Callout type="info" title="Revisions">
  **2026-06-09**: the original draft assumed `compute_v1.InstancesAsyncClient` existed. It does not (Compute is a REST API and the generator emits no async client for it), so the watcher burst-polls with the sync client.

  **2026-10-27**: corrected details that had drifted from the code: the watcher timeout is 300 s (not 120 s), the outcome log line is `VM creation outcome` (not `vm.create.outcome`), and the sweep runs daily (not hourly). The Cloud NAT half of this decision is restated on its own in [ADR-011](#cloud-nat-egress-with-no-external-ips).
</Callout>

### Context

- Burst test (2026-06-09): 18 jobs across 6 workflow runs in about 20 seconds. The orchestrator handled all 18 webhooks and logged `Submitted VM creation` for each.
- About 10 of the 18 VMs then failed inside GCE with `QUOTA_EXCEEDED` on `IN_USE_ADDRESSES` (the default external-IP quota in europe-west4 was 8, and each VM claimed one).
- The orchestrator never knew. It submitted the insert, logged it, and walked away without checking the operation's result.
- Diagnosis took cross-system log correlation: orchestrator logs, GCE audit logs, and GitHub job status.

Two coupled problems: a GCE quota constraint, and no self-observability.

### Options considered

**For visibility into VM creation outcomes**:

- **Sweep-only detection**: cheap, but the sweep runs once a day, far too late to explain a job that never got a runner.
- **Wait in the webhook handler**: blocks the response for the whole VM creation, blowing GitHub's 10-second webhook timeout. Rejected.
- **One blocking thread per VM** (`asyncio.to_thread(operation.result, ...)`): parks a thread-pool worker for the whole creation; a burst starves the pool. Rejected.
- **Burst-polling in a `BackgroundTasks` watcher** (chosen): the webhook returns immediately; the watcher polls the zone operation in short thread hops with `asyncio.sleep(1)` in between, so the pool is free between polls.
- **Cloud Tasks / Pub/Sub worker queue**: the cloud-native answer, but overkill at this scale.
- **Retry in the orchestrator**: rejected. Retrying doesn't help with the failure we actually saw (quota doesn't free up in time), and the state tracking costs more than rare transient failures justify.

**For the quota constraint**: per-VM external IPs (status quo), Cloud NAT (chosen, see [ADR-011](#cloud-nat-egress-with-no-external-ips)), or only asking for more quota.

### Decision

- Keep the sync `compute_v1.InstancesClient` bridged with `asyncio.to_thread`, plus a `ZoneOperationsClient` for polling. Both are created in the FastAPI lifespan.
- After `handle_queued` returns an `OperationHandle`, `main.py` schedules `compute_client.wait_for_vm_creation` as a background task. The task re-installs a snapshot of the request's log context (`logger.with_log_context`) so `request_id`, `job_id`, and `repo` stay on its logs.
- The watcher polls until the operation is `DONE` or until its 300 s timeout, then logs one `VM creation outcome` line with `outcome` (`success`, `failure`, or `timeout`), `op_name`, `zone`, `duration_ms`, `machine_type`, `spot`, `image_version`, and on failure `error_code` and `error_message`.
- The `vm_creation_outcome_count` metric feeds the `VM creation failure ratio > 5% (5m)` alert.
- The sweep stays as the safety net for watchers lost to a redeploy, OOM, or manual termination.

### Consequences

- **Pro**: every VM creation outcome is a structured log line and a metric. Root cause no longer needs cross-system correlation.
- **Pro**: a failed creation is visible within the watcher's 300 s window instead of at the next sweep.
- **Pro**: the thread pool is only busy during each short poll.
- **Trade-off**: a watcher interrupted by a deploy, OOM, or manual termination never logs its outcome. The sweep catches the VM; the metric misses it.
- **Trade-off**: no auto-recovery. If GCE rejects a VM, the GitHub job waits without a runner. Revisit if transient failures become common.

## Spot VMs and the runs-on label grammar

### Context

Phase 1 used one fixed machine type. Jobs differ a lot in what they need, and many CI jobs tolerate being interrupted, which makes Spot VMs (much cheaper, but GCE can reclaim them at any time) attractive. Users need a way to ask for a size and for Spot from `runs-on`, which is the only input a workflow gives us.

### Options considered

- **Fixed machine type**: simple, but wastes money on small jobs and starves big ones.
- **Named sizes only** (`small`, `medium`, ...): easy to read, but closes off every other GCE type.
- **Literal GCE machine types only**: flexible, but verbose, and typos fail at VM creation time.
- **Named sizes plus a literal escape hatch, Spot as an opt-in flag** (chosen).

### Decision

`machine_policy.resolve_labels` turns `runs-on` labels into a machine type and a Spot flag. Matching is case-insensitive.

| Label | Meaning |
|---|---|
| `runnerforge` | Required. Routes the job to RunnerForge. |
| `spot` | Create a Spot VM. |
| `self-hosted`, `linux`, `x64` | GitHub's default runner labels. Accepted and ignored. |
| `small` / `medium` / `large` / `xlarge` | `n2-standard-2` / `-4` / `-8` / `-16` |
| A literal type such as `n2-highmem-4` | Must match `^[a-z][a-z0-9]+-[a-z]+(?:-\d+)?$` and exist in the zone. |
| (no size) | `n2-standard-4` |

- At most one size token. Two sizes (named or literal) are rejected as `conflicting_machines`. A label that is neither a known label nor shaped like a machine type (for example `windows`, `macos`, `arm64`) is rejected as `unknown_token`. A hyphenated label such as `ubuntu-latest` has the literal shape, so it is treated as a machine type and rejected as `invalid_machine_type` when the zone has no such type.
- Literal types are checked against the zone's machine-type list, loaded once at orchestrator startup. If that list can't be loaded, the check is skipped and GCE rejects bad types at insert.
- A rejected job logs `Machine policy rejected` (metric `machine_policy_reject_count`) and gets no VM.
- Spot VMs use `provisioning_model = SPOT`, `automatic_restart = false`, `on_host_maintenance = TERMINATE`.
- When a job ends `failure` or `cancelled`, a background task queries the audit log for `compute.instances.preempted` on that VM and, on a match, logs `Job ended due to spot preemption` (metric `job_preempted_count`).

### Consequences

- Spot is opt-in per job, so nobody gets interrupted without asking for it.
- A preempted job fails. There is no automatic retry; the user re-runs it. The preemption log line tells them why.
- Spot VMs consume the same family CPU quota as on-demand ones (`N2_CPUS` for n2), not `PREEMPTIBLE_CPUS` (verified in `infra/terraform/quotas.tf`).
- A typo in `runs-on` leaves the job queued with no runner. The only signal is the rejection log, which users can't see yet.
- The orchestrator SA needs `roles/logging.viewer` for the audit-log query.

## Cloud NAT egress with no external IPs

### Context

Runner VMs originally each claimed an ephemeral external IP. The `IN_USE_ADDRESSES` quota capped concurrent VMs and caused the failed burst in [ADR-009](#self-observed-vm-provisioning-with-nat-based-egress). Self-hosted runners only make outbound connections (to GitHub and whatever the job downloads); nothing needs to reach them.

### Options considered

- **Per-VM external IPs**: status quo, bounded by quota, and every runner is reachable from the internet.
- **Quota increase only**: moves the ceiling without changing the design.
- **Cloud NAT** (chosen): one regional gateway for all outbound traffic; VMs have private IPs only.

### Decision

- `compute_client.create_vm` attaches the VM to `global/networks/default` with no access config, so it has no external IP.
- `infra/terraform/network.tf` defines router `runnerforge-nat-router` and gateway `runnerforge-nat` in europe-west4, covering only the `default` subnetwork (`LIST_OF_SUBNETWORKS`), with `nat_ip_allocate_option = "AUTO_ONLY"` and errors-only logging.

### Consequences

- `IN_USE_ADDRESSES` no longer limits how many VMs can run.
- Runners can't be reached from the internet.
- The egress IP is not fixed. Allow-listing RunnerForge's egress at a destination (for example a self-hosted GitHub Enterprise Server) would need a reserved address and `MANUAL_ONLY`.
- NAT adds a small gateway and per-GB processing cost.

## OpenTelemetry traces exported to Cloud Trace

### Context

Logs say what happened; they don't show where the time went inside a webhook (GitHub token fetch, GCE insert, label lookups) or tie the `queued` and `in_progress` webhooks of one job together.

### Options considered

- **Logs only**: already in place, but timing across calls means hand-correlating timestamps.
- **Self-hosted tracing backend** (Jaeger, Tempo): another service to run.
- **OpenTelemetry SDK exporting to Cloud Trace** (chosen): vendor-neutral instrumentation, a managed backend in the same project, IAM-based auth.

### Decision

- `tracing.setup_tracing` runs only on Cloud Run (when `K_SERVICE` is set). It uses the `ALWAYS_ON` sampler, a `BatchSpanProcessor`, and `CloudTraceSpanExporter`, with service name `runnerforge-orchestrator`.
- FastAPI and HTTPX are auto-instrumented. Handlers and `compute_client` add manual spans (`webhook.handle_queued`, `compute.create_vm`, `compute.wait_for_vm_creation`, and others).
- `queued` stores its outer request span's ids in the VM labels `webhook_trace_id` and `webhook_span_id`. `in_progress` parents its span under that anchor, so registration renders as one trace. `completed` starts its own trace and adds a span link back, because hours of job runtime would swamp a merged timeline.
- The orchestrator SA has `roles/cloudtrace.agent`.

### Consequences

- One trace shows the full runner registration for a job.
- Sampling everything is fine at current volume; revisit the sampler if trace cost grows.
- Instrumentation is OpenTelemetry, so changing backend means changing the exporter, not the spans.
- Tests and local runs don't export traces.

## Runner image pinned at startup with deprecate-then-delete retention

### Context

Runner images are built by Packer and published into the image family `runnerforge-runner`. Booting from the family alias means every VM resolves "latest" separately, so a promotion mid-burst mixes images and logs can't say which image a VM ran. Old images also pile up, and deleting them outright loses forensics and makes rollback harder.

### Options considered

- **Boot every VM from the family alias**: always newest, but no stable per-instance version and nothing to attribute failures to.
- **Pin an image in config**: exact, but every image release would need an orchestrator change.
- **Resolve the family once per orchestrator instance, then pin by name** (chosen).
- **Retention by hard delete**: simple, but irreversible.
- **Deprecate first, delete later** (chosen).

### Decision

- On startup (since orchestrator 0.11.0), `compute_client.init_runner_image` calls `get_from_family` for `runnerforge-runner` in `RUNNER_IMAGE_PROJECT` (defaults to `GCP_PROJECT_ID`) and boots every VM from `projects/<project>/global/images/<name>`. The parsed version is logged and becomes the `image_version` label on `vm_creation_count` and `vm_creation_outcome_count`.
- If the lookup fails, VMs boot from the family alias and a warning is logged.
- The `Retention` step of `.github/workflows/deploy-runner-image.yaml` keeps the five newest non-deprecated images in the family and deprecates the rest with `delete-on` 30 days out. Rollback also deprecates (with the same 30-day `delete-on`) instead of deleting; the family then serves the next-newest non-deprecated image.
- The `ci-runner-image-build` SA uses the custom role `runnerImageManager` (8 `compute.images.*` permissions, `infra/terraform/runner_image.tf`) instead of `roles/compute.storageAdmin`.

### Consequences

- Every VM from one orchestrator instance uses one known image, and failures can be sliced by `image_version`.
- A newly promoted image reaches an orchestrator instance only when that instance starts (new revision, scale-up, or restart). Long-lived instances keep the older pin until then.
- Deprecated images stay available for 30 days for forensics and rollback.
- The retention step is `continue-on-error`, so a failure there doesn't fail an image release; it needs a look at the workflow log.

## GCE-enforced runtime cap with DELETE

### Context

A runner VM that never gets its `completed` webhook (lost delivery, a stuck job, a crashed orchestrator) keeps billing until something deletes it. The only backstop was the sweep, which runs once a day, so a stuck VM could bill for up to a day.

### Options considered

- **Sweep more often**: shortens the window, costs more Cloud Run and GitHub API calls, and still depends on our code being healthy.
- **Shutdown timer inside the VM**: relies on the guest, which is what is broken in the cases that matter.
- **GCE `max_run_duration` with `STOP`**: GCE enforces it, but a stopped VM's disks keep billing.
- **GCE `max_run_duration` with `DELETE`** (chosen).

### Decision

- Every VM gets `scheduling.max_run_duration = MAX_VM_RUN_DURATION` (6 h 15 min, `compute_client.py`) and `instance_termination_action = "DELETE"`. The action is always set explicitly, because it defaults to `STOP` for Spot.
- 6 hours matches GitHub's default job timeout of 360 minutes. The extra 15 minutes covers boot and registration.
- The sweep's hard limit (`sweep.HARD_LIMIT`) reuses the same constant. The sweep stays as the backstop for VMs created before this shipped (0.17.8) and for any lag in GCE's termination.

### Consequences

- A runaway VM can't bill longer than 6 h 15 min of running time, even if the orchestrator is down.
- Jobs that set `timeout-minutes` above 360 are cut off when their VM reaches 6 h 15 min.
- Boot and data disks are `auto_delete`, so deleting the VM removes them.
- The cap is global today. The code comment marks it to become a per-tenant limit; that is planned, not built.

## Installation allow-list as a stop-gap admission control

### Context

Any GitHub account that installs the App gets its `workflow_job` events sent to the orchestrator, and each `queued` event with `runnerforge` in `runs-on` creates a VM on RunnerForge's GCP project. The App is private today, but the plan is a free hosted beta with manual approval ([ADR-016](#multi-tenancy-scope-installation-as-tenant)). We need a way to decide who gets VMs before building a tenant system.

### Options considered

- **Rely on the App being private**: works only while it stays private, and gives no kill switch.
- **Tenant database with approval flow and limits**: the long-term answer, but a lot to build before the first external user.
- **Allow-list of installation IDs in config** (chosen): small, reviewable, applied through Terraform.

### Decision

- Terraform variable `allowed_installation_ids` (`infra/terraform/variables.tf`) becomes the Cloud Run env var `ALLOWED_INSTALLATION_IDS`, a comma-separated list.
- `config.parse_installation_ids`: unset allows every installation (`main.py` logs a warning at startup); an empty string allows nobody (a kill switch); a malformed ID raises at import, so a bad revision fails its canary. The Terraform variable also rejects non-numeric IDs before they reach Cloud Run.
- Only `queued` events are gated. A rejected installation gets 200, an `Installation not allowed` warning, and no VM. `in_progress` and `completed` always pass, so an installation removed mid-job still has its VMs cleaned up.
- `Webhook event received` is logged after the gate, so rejected installations don't trip the lost-webhook alert.

### Consequences

- Approving a tenant is a Terraform change plus an orchestrator release: production traffic is pinned to a named revision, and the revision Terraform creates gets no traffic, so the new value takes effect with the next CD deploy (see the comment in `cloud_run.tf`).
- No per-installation limits yet. An approved installation can use as much capacity as the project quotas allow.
- This is a stop-gap. It goes away or becomes a seed list once a real tenant store exists.

## Multi-tenancy scope: installation as tenant

### Context

RunnerForge started as a single-owner tool. Opening it up raises a set of questions: what a tenant is, whose GCP project VMs run in, and who pays.

### Options considered

- **Tenant = GitHub App installation** (chosen) vs. tenant = repository or tenant = RunnerForge account.
- **Where VMs run**: RunnerForge's own project (hosted), the user's own deployment of the whole backend (self-host), or the user's GCP project driven by our orchestrator (bring-your-own-project).
- **Billing**: free beta vs. paid plans.

### Decision

- **A tenant is one GitHub App installation**, which means one GitHub user or organization. Personal accounts and organizations are both supported. VMs carry `installation_id` as a label, and the delete path checks it ([ADR-004](#gce-vm-labels-over-a-database-for-state-tracking)).
- **Hosted, free beta**: VMs run in RunnerForge's GCP project. Access is by manual approval through the allow-list ([ADR-015](#installation-allow-list-as-a-stop-gap-admission-control)). Per-installation limits are planned.
- **Self-hosting the whole backend** is planned as the other way to run RunnerForge. `RUNNER_IMAGE_PROJECT` (0.17.8) already decouples the image project from the project VMs run in.
- **Deferred**: bring-your-own-GCP-project mode and paid billing. Neither is being built.

### Consequences

- The isolation boundary between tenants is the VM ([ADR-002](#gce-vms-over-kubernetes-pods-for-runners)) plus the installation check on deletes. All tenants share one project, network, runner SA, and quota.
- Capacity is shared: until per-installation limits exist, one tenant's burst can use up the project quota for everyone.
- Labelling disks with `installation_id` (0.17.8) makes per-tenant cost attribution possible from the billing export.
- The App is private today. The allow-list is what makes opening it up safe: a new installation gets no VMs until its ID is added.

## Docs site: static export on Cloudflare Workers

### Context

- The docs site (`apps/web`, Next.js + Fumadocs) was deployed on Vercel. Vercel's Hobby plan is for non-commercial use only, the project that owned `runnerforge.com` was paused (the domain returned 503), and the DNS zone already lives on Cloudflare.
- The docs are public, read-only content. Nothing on them needs a server at request time.
- The dashboard is an authenticated app with different needs. It is out of scope here and gets its own ADR.

### Options considered

- **Stay on Vercel**: no migration work, but Hobby forbids commercial use and Pro is a monthly seat for a site that needs no server.
- **Static export on Cloudflare Workers static assets**: no server to run; static asset requests are free.
- **Container on Cloud Run**: possible, but a server we don't need for static docs.

### Decision

- `next.config.mjs` sets `output: 'export'`; every route is pre-rendered (`revalidate = false`, `generateStaticParams`).
- Served by the assets-only Worker `runnerforge-web` (`apps/web/wrangler.jsonc`) on the custom domain **`runnerforge.com`**. Cloudflare manages the DNS record and certificate. `www` is a proxied placeholder record with a Redirect Rule to the apex. The production `workers.dev` URL is off.

A merge to `main` builds `apps/web` and runs `wrangler deploy`; other branches run `wrangler preview` (Workers Previews) and get a per-branch preview URL (`<branch>-runnerforge-web.runnerforge.workers.dev`, posted on the PR). This needs `preview_urls: true` and the `previews` block in `wrangler.jsonc`.

- OG images and the `llms` routes are generated at build time.
- Builds run on Cloudflare (Free plan: 3,000 build minutes a month, 1 concurrent build), outside the repo's GitHub Actions conventions. The PR gate (`qualify.yaml`) still lints, type-checks and builds `apps/web` before merge.
- Preview URLs are public; acceptable for public docs. Cloudflare Access can protect them later.
- The `web` release-please component still produces versions and changelogs; deploys follow merges to `main`, not releases.

## Per-job state in Firestore behind a JobStore protocol

<Callout type="info" title="Revisions">
  **2026-10-30**: accepted with R1 (Terraform). `roles/editor` lacks `datastore.databases.create`, so the apply SA got a custom `firestoreDatabaseCreator` role, created out-of-band and adopted by `terraform_ci.tf`. R2 and R3 are not built yet.

  **2026-10-30** (R2): `errored` is recorded in `handle_queued` around each failing call, so its stage is exact, instead of by an `except` in `main.py`. Facts that can land after `completed` (the VM watcher's `vm`, the cross-check's `preempted`) no longer reopen the record. A `queued` that finds a closed record logs the new outcome `already_completed` and writes no decision. The timeout is a fixed 2 s hard bound rather than one tuned from measurements, and a `queued` request whose create fails skips its other writes. A background fact that finds no record creates it with `open: true`. The `Job store write failed` metric and alert are not built yet. R3 is not built yet.
</Callout>

### Context

- What happened to a job exists only in log lines today: `Machine policy rejected`, `Queued webhook outcome`, `VM creation outcome`, `Job ended due to spot preemption`, and the rest. The dashboard needs each job's true status, with advice such as "fix `runs-on`" or "cancel and re-run". The tenant registry and its limits, and usage tracking, need per-installation reads (phases 4.2 and 4.4 on the [roadmap](/docs/development#phase-41-onward-planned)). Logs can't serve any of these: Cloud Logging's `entries.list` quota is 60 requests a minute per project, can't be raised, and the preemption cross-check already spends it.
- GitHub delivers `workflow_job` webhooks out of order, never retries them, and gives the handler 10 seconds. A state machine that assumes `queued → in_progress → completed` breaks on the first reordered delivery.
- Three facts happen outside any request:
  - **VM creation outcome**: logged by a post-response background task ([ADR-009](#self-observed-vm-provisioning-with-nat-based-egress)). With `cpu_idle = true` that task is best-effort.
  - **Mid-job preemption**: found by the `cross_check_preemption` background task after `completed`.
  - **Preemption before pickup**: no webhook and no orchestrator log line. Only the GCE audit log `compute.instances.preempted` records it, and GCE deletes the VM, so the sweep never sees it either. This is what left a job queued for good on 2026-10-28.
- GitHub gives a queued job to any idle runner whose labels match. The VM created for job A can run job B. The `completed` path already deletes the VM named in `runner_name` for this reason, so a VM's name says which job caused it, not which job it ran.
- Cloud Run instances of the old and new revision serve traffic at the same time (5% canary, rollback), so the record format has to change by expand/contract.
- The whole backend should be self-hostable later ([ADR-016](#multi-tenancy-scope-installation-as-tenant)).

### Options considered

Monthly costs are list prices for europe-west4, checked on 2026-10-28, at about 50k jobs a month.

- **Firestore Standard, Native mode** (chosen): about $0–1, nothing billed when idle, an async Python client (`AsyncClient`), Terraform resources for the database, TTL and indexes, and schemaless documents, which suits expand/contract. Can't be self-hosted, and there's no emulator in our tests.
- **Cloud SQL for PostgreSQL** (`db-f1-micro`): real SQL, and the same engine a self-hoster would run. About $10 a month even when idle, a shared-core tier with no SLA, a 25-connection default, and schema migrations across overlapping revisions.
- **Spanner, AlloyDB**: minimums of $65+ a month, and neither scales to zero.
- **Neon, Supabase**: Neon scales to zero but wakes in hundreds of milliseconds, runs only in AWS regions, and needs a long-lived password, which breaks the no-long-lived-secrets rule ([ADR-007](#workload-identity-federation-over-service-account-keys-for-ci-auth)). Supabase Pro starts at $25.
- **Cloudflare D1**: free, but from Cloud Run its REST API is an account-wide control-plane path (1,200 requests per 5 minutes). Using it properly would need a Worker in front that verifies Google ID tokens.
- **GCS objects, BigQuery, Cloud Logging as the store**: no indexed queries, write and DML limits, or the 60/min read cap.
- **No store**: the dashboard calls GitHub live and limits count GCE VMs. No history, and no record of the states that never reach a VM (rejected, errored).

For facts outside requests: a Cloud Scheduler reconciler; a log sink to Pub/Sub push to an authenticated endpoint; Eventarc (its filters are exact-match only, and it reports Compute events as `us-central1`); Cloud Tasks per job (still can't see preemption); or the daily sweep only.

### Decision

**Store.** A Firestore Standard, Native-mode database named `runnerforge`, regional in `europe-west4`, created by Terraform with delete protection and point-in-time recovery on. The orchestrator SA gets `roles/datastore.user` with an IAM condition that limits it to that database (`firestore.tf`), in the form Firestore's per-database access docs give.

**Record.** One document per job in a top-level `jobs` collection. Its ID is `{run_id}-{job_id}-{run_attempt}`, the VM name without `runnerforge-`. The ID includes `run_attempt`, so it stays unique whether or not GitHub reuses `job_id` on a re-run (GitHub doesn't document which).

| Field | Holds |
|---|---|
| `installation_id`, `repository_id`, `repo`, `run_id`, `job_id`, `run_attempt`, `labels` | Identity. `repo` is `owner/name`, needed to ask GitHub about the job. |
| `queued_at`, `expire_at`, `schema_version` | `queued_at` is the payload's `workflow_job.created_at`, or the time received if that is missing. `expire_at` is `queued_at` plus 90 days and drives a TTL policy; it is exempt from indexing. |
| `open`, `next_check_at` | `open` is `false` once the job is closed. `next_check_at` is when the reconciler should look at the job again. |
| `decision` | `kind` (`vm_submitted`, `already_exists`, `policy_rejected`), plus `reason`, `offending_tokens`, `machine_type`, `spot` |
| `errored` | `stage` (`token` or `gce_insert`) and `error_class`, when the `queued` path raised before a decision |
| `vm` | Creation `outcome` (`success`, `failure`, `timeout`, `missing`), `error_code`. `timeout` only means the watcher stopped polling; the VM may still have started. |
| `in_progress`, `completed` | `runner_name`; `conclusion` |
| `preempted` | `phase` (`before_pickup` or `mid_job`) |

Every fact is a sub-map that carries `at` and `source` (`webhook`, `watcher` or `reconcile`). The record holds facts, not a status. One pure function derives the status when the record is read. Rows are checked top to bottom and the first match wins, so a reordered delivery can't move a job backwards:

| Facts | Derived status |
|---|---|
| `completed` | Done, with `conclusion` and any `mid_job` preemption |
| `in_progress` | Running |
| `decision.kind = policy_rejected` | Rejected: fix `runs-on` (shows `reason`, `offending_tokens`) |
| `errored` newer than any `decision`, or `vm.outcome = failure` | Failed to start: re-run |
| `preempted.phase = before_pickup`, or `vm.outcome = missing` | Stuck: cancel and re-run |
| anything else | Starting. The dashboard shows it as late once it passes a threshold of its own, at least the 5-minute Time-to-Register SLO. |

**Writes.** Every write is a field-level merge (`set(..., merge=True)`) of one fact plus the base fields: identity, `queued_at`, `expire_at`, `schema_version` and `next_check_at`. That way a record created by whichever event arrives first still gets its TTL and is visible to the reconciler. Writing the same fact twice changes nothing, so no transactions are needed. A `completed` write sets `open: false`. Webhook facts set `open: true`, so a late `in_progress` can reopen a completed record; the reconciler closes it again on its next check. The background tasks' facts (`vm`, `preempted`) leave `open` alone, because they can land after `completed`.

The one conditional write is on the `queued` path, after admission: `create()`. If the document already exists and `open` is `false`, `completed` arrived first, so the handler skips the VM, logs the `Queued webhook outcome` `already_completed`, and writes no decision (which would reopen the record). In every other case it carries on, and GCE's `AlreadyExists` on the VM name decides duplicates, as it does today.

| Fact | Written at |
|---|---|
| `decision` | `handle_queued`, next to each `Queued webhook outcome` line |
| `errored` | `handle_queued`, around the token fetches (`token`) and the GCE insert (`gce_insert`): records the fact and re-raises, so the response is still 500 with no outcome line. Failures in `in_progress` and `completed` handling stay log-only. |
| `in_progress`, `completed` | `main.py`, before the handler runs, so a failing GCE lookup in the handler doesn't lose the fact |
| `vm` | `wait_for_vm_creation` (best-effort). `OperationHandle` carries the job key and base fields. |
| `preempted` (`mid_job`) | `cross_check_preemption`, positive result only (best-effort). `PreemptionCheckRequest` carries the job key and base fields. |
| anything still missing | The reconciler |

Only installations that pass admission get records. `Installation not allowed` stays log-only, and `in_progress` and `completed` facts are written only for allowed installations, even though those events skip the admission gate. Once the App is public, writing a document for every unapproved installation's jobs would let anyone grow the store. An installation removed mid-run gets its record closed by the reconciler. Approval state belongs to the tenant registry.

**Failure policy: fail open.** Every store call runs inside a hard 2 s `asyncio.timeout` and retries only on `UNAVAILABLE` (the client's own `timeout=` bounds one attempt, and its default write retry lasts 60 s). On timeout or error, the handler logs `Job store write failed` (operation, error class), does not write the record, and carries on, so the job still gets its VM. On the `queued` path, a failed or timed-out create skips that request's other store writes, so a degraded store adds at most about 4 s to a webhook (today's slowest `queued` request takes 2.3 s of GitHub's 10 s). GitHub never retries, so failing closed would turn a store outage into stuck jobs for every tenant. The reconciler fills most of the gaps. A log-based metric and an alert on `Job store write failed` follow once the release that writes is at 100%.

**Reconciler.** `POST /reconcile`, called by a second Cloud Scheduler job every 5 minutes and authenticated like `/sweep` (`verify_oidc_token`). Each run:

1. Queries `open == true` jobs whose `next_check_at` has passed, earliest first, up to a fixed batch. It logs how many it left for the next run. New records start with `next_check_at` 5 minutes after `queued_at` (the Time-to-Register SLO threshold). Each check pushes it back with a backoff, longer for jobs already known to be rejected or running, so jobs that can't be closed yet don't crowd out new ones.
2. Lists `runnerforge` VMs once. It makes one paged `entries.list` query for `compute.instances.preempted` on `runnerforge-*` VMs, from the oldest `queued_at` in the batch (capped at 24 hours) to now. That is one logical query per run, against the 60-a-minute quota. A VM with no record (its `queued` write failed) gets one, built from its GCE labels and its `repo-url` and `runner-labels` metadata, with `queued_at` from the `queued_received_at` label.
3. For each job, calls GitHub `GET /repos/{repo}/actions/jobs/{job_id}`:
   - A completed job gets its `completed` fact. A 404, or an installation token that can't be fetched, writes `completed` with `conclusion: gone`. Either way the record is closed.
   - A job still queued is matched to VMs by `in_progress.runner_name` across records, not by VM name. If its own VM is gone and no other RunnerForge VM for the same repository could still pick it up, it gets `preempted` (`before_pickup`) when the audit query names that VM, and `vm.outcome = missing` when it doesn't. Otherwise it waits for a later check. A preempted VM that appears as another job's `runner_name` is that job's `mid_job` preemption.
   - A VM that exists with no `vm` fact gets `success`. Records with a `policy_rejected` decision or an `errored` fact get no `vm` facts.
   - Every fact it writes has `source: reconcile`.
4. Logs one `Reconcile completed` line with counts.

Nothing here is GCP-specific beyond the GCE and Logging clients, so a self-hosted install keeps the reconciler. The push path (log sink → Pub/Sub → an OIDC-authenticated `/events/gce`) is deferred. It would deliver preemptions in seconds instead of minutes. On GCP it would also let `cross_check_preemption`, the reconciler's audit query (step 2) and `roles/logging.viewer` be removed; an install without the push path keeps the query and the role. It is blocked on two checks: whether GCE insert audit entries contain the registration-token metadata, and how a sink follows VMs into a separate pool project (4.3).

**What stays as it is.** VM labels and metadata remain the authority for which VMs exist, who owns them, and what the delete paths and the sweep act on ([ADR-004](#gce-vm-labels-over-a-database-for-state-tracking)). Log lines and log-based metrics remain the source for metrics, SLOs and alerts ([ADR-006](#structured-logging-over-firestore-for-initial-observability)). The store adds to both and replaces neither. Every existing log line stays.

**Self-host seam.** The orchestrator talks to a `JobStore` Protocol (`record_fact`, `create_if_absent`, `get`, `list_by_installation`, `list_due`, `count_open`), never to the Firestore client directly. A `JOB_STORE` setting selects `firestore` or `none` (a no-op; the default when unset). Tests use an in-memory fake for handler behaviour and patch `AsyncClient` in `conftest.py` for the adapter, the same way the GCE clients are patched. A SQL adapter (SQLite for one process, Postgres for more) ships with the self-host work, not before. SQLite is single-process only, because Cloud Run's GCS volume mounts have no file locking.

**Not decided here.** The tenant-registry ADR (4.2) decides:

- how usage limits count active VMs (from the store or from a GCE list);
- whether limits are hard or soft;
- what happens when an admission read fails.

Counting from the store can overshoot by a whole matrix burst, because concurrent webhooks read the count before any of them write.

### Rollout

1. **R1, Terraform:**
   - Enable `firestore.googleapis.com`.
   - Add the database, the `expire_at` TTL field, the `(installation_id, queued_at)` and `(open, next_check_at)` indexes, and the IAM binding.
   - The apply SA can't create Firestore databases: `roles/editor` lacks `datastore.databases.create`. A custom `firestoreDatabaseCreator` role is created and granted out-of-band first, then adopted by `terraform_ci.tf`.
2. **R2, orchestrator writes:**
   - Add the protocol, the fake, the Firestore adapter and the write points. Terraform sets `JOB_STORE` first.
   - Nothing reads the records yet. A revision that doesn't write is harmless, so the canary and rollback are safe.
   - Check every query against the production database (Query Explain) before anything reads from it.
   - In the same release, update the docs that say there is no database: `AGENTS.md`, `docs/index.mdx`, and "What we store, and where" in `trust.mdx`.
3. **R3, reconciler:**
   - Add `/reconcile`, the Scheduler job and the `Reconcile completed` metric.
   - In the same release, add a revision note to ADR-001, whose consequences list `/sweep` as the only Scheduler-driven work.
   - In the same release, add the jobs call and the 5-minute token mint to the list of GitHub API calls in `trust.mdx`, and the reconciler to the Actions: Read rationale in `trust.mdx` and `architecture.mdx`.
4. **Later:** a read API for the dashboard (4.5), the tenant registry (4.2), the push path and its contract step.

Readers must tolerate missing fields and check `schema_version`, because a document may have been written by an older revision.

### Consequences

- About $0–1 a month at beta scale, with nothing billed when idle. The reconciler calls Cloud Run 288 times a day, each billed only for its request time. That is the first scheduled traffic beyond the daily sweep.
- **Coverage gaps:**
  - Out-of-band facts arrive within about 5 minutes (one reconciler interval), later if the batch is full.
  - A job whose `queued` write failed during a store outage gets a record only if its VM still exists when the reconciler runs.
  - A rejected or errored job whose write failed has no record at all; its details stay in the logs only.
- A new dependency (`google-cloud-firestore`) and a new failure mode on the webhook path, bounded by the timeout and fail-open.
- No emulator means the fake can't catch Firestore index or query mistakes, and there is no staging project. R2's check against the production database covers that.
- **Data held:**
  - Records hold repository names, GitHub job IDs, runner names and labels for 90 days. They hold no tokens.
  - TTL deletion can lag by up to a day after `expire_at`, so readers also filter on it.
  - Deleting an installation's records when the App is uninstalled needs the `installation` event, which 4.2 adds. Until then, the TTL bounds how long they stay.
- Two places describe a job: GCE for the VM and the store for its history. When they disagree about whether a VM exists, GCE wins, and the reconciler brings the record into line.
