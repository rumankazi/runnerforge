## Request path: `/webhook`

Cloud Run is public (`INGRESS_TRAFFIC_ALL`, `allUsers` as `roles/run.invoker` in `cloud_run.tf`) because GitHub delivers webhooks from changing IP addresses. All authentication happens in the app. A webhook goes through these checks in order (`main.py`, then `handlers.py` for the machine policy):

1. **HMAC signature.** The orchestrator computes `sha256=` + HMAC-SHA256 of the raw body with the webhook secret and compares it to `X-Hub-Signature-256` using `hmac.compare_digest` (`security.py`). A mismatch returns 401. The warning log keeps only the first 10 characters of the header.
2. **Event type.** Dispatch is on the `X-GitHub-Event` header, never on payload shape. `workflow_job` drives runners. `installation` events update the tenant registry ([ADR-019](/docs/design/decisions#tenant-registry-install-to-register-admin-approval-per-installation-limits)); they can create a `pending` row or change GitHub's status of a row, never approve one. `ping` and every other event get a 200 and are ignored before the body is parsed.
3. **RunnerForge label.** A job without the `runnerforge` label (case-insensitive) is acknowledged and skipped.
4. **Installation allow-list.** For `queued` events, an installation not listed in `ALLOWED_INSTALLATION_IDS` gets a 200, an `Installation not allowed` warning, and no VM. `in_progress` and `completed` always pass, so VMs of an installation removed mid-job are still cleaned up. The `Webhook event received` log line is written after this gate, so rejected installations don't count toward the lost-webhook ratio.
5. **Machine policy.** `machine_policy.py` resolves labels to a machine type. GitHub's default runner labels `self-hosted`, `linux` and `x64` are accepted as no-ops. Any other unknown label, including `windows`, `macos` and `arm64`, rejects the job. Literal machine types (for example `n2-standard-8`) are checked against the zone's machine-type list, which is loaded at startup. If that list can't be loaded, the check is permissive and GCE rejects an invalid type at create time.

### Allow-list semantics

`ALLOWED_INSTALLATION_IDS` is parsed once at startup (`config.py`):

| Value | Effect |
|---|---|
| Unset | Every installation can create VMs. A startup warning is logged. This is meant for a self-hosted, private App. |
| `""` (empty) | Nobody can create VMs. Works as a kill switch. |
| `123,456` | Only those installation IDs can create VMs. |
| Malformed ID | `config.py` raises at import, so the new revision fails to start and the deploy stops at the canary step. |

In production, Terraform sets it from `var.allowed_installation_ids` (`variables.tf`, `cloud_run.tf`), and the variable validates that every ID is numeric. CD builds each orchestrator revision from the current service template, while the revision Terraform creates gets no traffic. **A change to the list therefore takes effect with the next orchestrator release**, not with the Terraform apply.

<Callout type="warn" title="No per-installation limits yet">
  The allow-list is the only per-tenant gate today. Within it, a single installation can request any valid machine type and as many concurrent jobs as GitHub sends. The ceilings are project-wide GCE quotas in `europe-west4`, which every installation shares: the quota preferences in `quotas.tf` (200 instances, 1,500 GB SSD) and GCP's default per-family CPU quotas. Per-installation limits are planned.
</Callout>

## Request paths: `/sweep` and `/reconcile`

`/sweep` is called by the Cloud Scheduler job `runnerforge-sweep` daily at 00:12 UTC (`scheduler.tf`), and `/reconcile` every 5 minutes by `runnerforge-reconcile` (ADR-018). Both use the same identity and checks. Each job sends a Google-signed OIDC token as the `runnerforge-scheduler` service account, with the Cloud Run URL as audience. `verify_oidc_token` (`security.py`) requires all of the following, and returns 401 otherwise:

- a `Bearer` prefix
- a valid Google signature, issuer and expiry, and an audience equal to `EXPECTED_AUDIENCE`
- an `email` claim equal to `EXPECTED_SCHEDULER_SA_EMAIL`
- `email_verified` set to true

`/health` is unauthenticated and only returns `{"status": "ok"}`.

## VM lifecycle controls

### Deleting on `completed`

`runner_name` in a `completed` payload is chosen by whoever registered the runner, so the name alone proves nothing. `handlers.handle_completed` deletes a VM only when all of these hold:

1. `runner_name` starts with `runnerforge-`. Other runners are normal traffic, so a non-matching name is logged at info level and skipped.
2. The VM exists, which `compute_client.get_vm_labels_by_name` checks. A missing VM isn't deleted again, but a failed or cancelled job still gets the preemption cross-check, and only for allow-listed installations, with the name matched exactly in the audit-log query.
3. The VM's own labels have `runner=runnerforge` and an `installation_id` equal to the event's installation.

Failing check 3 logs `Refusing to delete VM not owned by this installation` and deletes nothing. A signed webhook from installation A therefore can't delete installation B's VM.

### Runtime cap

Every VM is created with `scheduling.max_run_duration` of 6h15m and `instance_termination_action = DELETE` (`compute_client.MAX_VM_RUN_DURATION`). GCE deletes the VM itself, even if the orchestrator is down. 6h matches GitHub's default job timeout, and the extra 15 minutes covers boot and registration. Both disks are `auto_delete` and carry the instance's labels.

### Sweep

`sweep.run_sweep` lists VMs labeled `runner=runnerforge` and skips any whose labels don't validate. For each VM it decides as follows:

| VM age | Decision |
|---|---|
| Under 1 hour | Skip. The webhook path owns it. |
| Over `HARD_LIMIT` (the same 6h15m) | Delete, whatever the runner is doing. |
| In between | Read the exact `owner/repo` from the VM's `repo-url` metadata and ask GitHub whether the runner on this VM (same name) is busy. Busy: skip. Idle or no longer registered: delete. Repo 404, or the repo can't be read: skip and never guess, so only the hard limit applies. |

## GitHub App credentials

`github_client.py` uses three tokens in sequence:

| Token | Created by | Lifetime | Where it lives |
|---|---|---|---|
| App JWT | RS256 with the App private key, `iat` = now − 60s, `exp` = `iat` + 600s | about 9 minutes | In memory, per call |
| Installation access token | `POST /app/installations/{id}/access_tokens` | 1 hour (set by GitHub) | In memory. Fetched for each `queued` job; the sweep caches one per installation for a single run. Never persisted. |
| Runner registration token | `POST /repos/{owner}/{repo}/actions/runners/registration-token` | 1 hour (set by GitHub) | Written to the VM's `registration-token` metadata key for the startup script |

The installation token response is validated against a model that requires the `actions`, `metadata` and `administration: write` permissions (`models.py`). Token requests are **not** narrowed to a single repository or permission subset, so each installation token carries everything the installation granted.

The registration token stays in VM metadata for the VM's lifetime. Any process on the VM can read it from the metadata server, and so can any principal with `compute.instances.get` in the project.

## Secrets

Both secrets are in Secret Manager with automatic replication (`secrets.tf`):

| Secret | How the orchestrator gets it |
|---|---|
| `github-app-private-key` | A Cloud Run secret volume, mounted as a file at `/secrets/github-app-private-key`. `GITHUB_APP_PRIVATE_KEY_PATH` points at that file. |
| `github-webhook-secret` | The `GITHUB_WEBHOOK_SECRET` env var, using `value_source.secret_key_ref` (version `latest`). The Cloud Run config holds a reference, not the value. |

Terraform creates only the secret containers. No `google_secret_manager_secret_version` exists in the configuration, so secret values never enter Terraform state. The orchestrator has `roles/secretmanager.secretAccessor` on these two secrets only, not on the project.

## Runtime identities

| Service account | Grants (source) | Notes |
|---|---|---|
| `runnerforge-orchestrator` (Cloud Run) | Project: `compute.instanceAdmin.v1`, `compute.imageUser`, `logging.logWriter`, `cloudtrace.agent`, `logging.viewer`; `datastore.user` limited by an IAM condition to the `runnerforge` Firestore database (`firestore.tf`). Per secret: `secretmanager.secretAccessor` on the two secrets. Per SA: `iam.serviceAccountUser` on `runnerforge-runner-vm` (`iam.tf`, `runner_vm.tf`) | `logging.viewer` is for the spot-preemption audit-log cross-check. `instanceAdmin.v1` is project-wide, so the ownership rules above are enforced in code, not IAM. |
| `runnerforge-runner-vm` (every runner VM) | Project: `logging.logWriter` only (`runner_vm.tf`) | The VM gets the `cloud-platform` scope, so IAM is the only limit. A job can get this SA's token from the metadata server, but can only write logs with it. |
| `runnerforge-scheduler` | No role bindings in Terraform (`scheduler.tf`) | It exists only as the identity in the `/sweep` and `/reconcile` OIDC tokens. |

On the runner image, the `runner` user isn't in `sudo` but is in the `docker` group (`infra/packer/scripts/install-runner.sh`). That makes it effectively root on its VM. Treat the VM as fully controlled by the job it runs.

## Network

- **No external IPs.** `create_vm` attaches only the `default` network interface, with no access config (`compute_client.py`).
- **Egress via Cloud NAT.** `runnerforge-nat` on `runnerforge-nat-router` (`network.tf`) NATs only the `default` subnetwork in `europe-west4`, using auto-allocated IPs, and logs errors only. See ADR-009 in [Decisions](/docs/design/decisions).
- **No inbound path.** Nothing needs to reach a runner VM. Runners poll GitHub outbound.
- **Firewall rules are not managed by Terraform.** All runner VMs, from every installation, share the project's `default` VPC, so network isolation between tenants is not enforced by RunnerForge config today.

## CI identity (Workload Identity Federation)

GitHub Actions authenticates to GCP with short-lived federated tokens. No service account keys exist (ADR-007 in [Decisions](/docs/design/decisions)). Everything here is in `wif.tf`, `terraform_ci.tf` and `runner_image.tf`.

**Provider gate.** The pool `github` and provider `github` trust `https://token.actions.githubusercontent.com` with:

```hcl
attribute_condition = "assertion.repository_owner == 'rumankazi' && assertion.repository == 'rumankazi/runnerforge'"
```

A token from any other repository, including forks, fails the exchange. The provider also maps `attribute.workflow_path` from `assertion.job_workflow_ref.split('@')[0]`, which is the workflow file without its ref.

**Per-SA bindings.** Each CI service account grants `roles/iam.workloadIdentityUser` to a narrower principal set:

| Service account | Who can impersonate it | Grants |
|---|---|---|
| `ci-build` | `workflow_path` = `.github/workflows/deploy-orchestrator.yaml` | `artifactregistry.writer` on the orchestrator repository, `run.developer` on the orchestrator service, `iam.serviceAccountUser` on the orchestrator SA |
| `ci-terraform-plan` | `attribute.repository` = `rumankazi/runnerforge`, which means any workflow in the repo (used by `_qualify-infra.yaml` and `drift-detection.yaml`) | Project `viewer` and `iam.securityReviewer`; `storage.objectUser` on the state bucket |
| `ci-terraform-apply` | `workflow_path` = `.github/workflows/deploy-infra.yaml`, which runs on push to `main` (or manual dispatch) in the `prod-infra` environment | Project `editor`, `iam.securityAdmin`, `iam.roleAdmin`, `secretmanager.admin`, the custom `firestoreDatabaseCreator` role; `storage.objectAdmin` on the state bucket |
| `ci-runner-image-build` | `workflow_path` = `.github/workflows/deploy-runner-image.yaml` | `compute.instanceAdmin.v1`, the custom `runnerImageManager` role, `logging.viewer`, `iam.serviceAccountUser` on `ci-vm-logger` |
| `ci-vm-logger` | No WIF binding. `ci-runner-image-build` attaches it to the Packer build VM and smoke-test VMs. | `logging.logWriter` |

`runnerImageManager` is a project custom role that replaced `roles/compute.storageAdmin`. It holds exactly these permissions: `compute.images.create`, `delete`, `deprecate`, `get`, `list`, `setLabels`, `update` and `useReadOnly`.

`firestoreDatabaseCreator` is a project custom role holding `datastore.databases.create`, `datastore.locations.get` and `datastore.locations.list`, which `editor` lacks. It has no delete permission; the database is delete-protected.

The `workflow_path` bindings pin a workflow **file**, not a branch. Which refs can run that file is controlled by the workflow's triggers and its GitHub environment: In `deploy-orchestrator.yaml`, the 5% canary runs without approval, while the 100% ramp and rollbacks are gated behind the `prod` environment. Orchestrator images are signed with keyless Cosign during the build.

## Infrastructure guardrails

Every infra PR runs `conftest test` against the Terraform plan JSON in `_qualify-infra.yaml`, using the policies in `infra/policies/`. Each policy has a `*_test.rego`.

| Policy | Blocks |
|---|---|
| `no_basic_roles.rego` | Any IAM binding with `roles/owner`, `roles/editor` or `roles/viewer`, except for `ci-terraform-plan` and `ci-terraform-apply` |
| `no_destroy_protected.rego` | Delete or replace of 15 critical resources, including the state bucket, the WIF pool and provider, every service account, the Cloud Run service, both secrets and the Firestore database. Removing one takes three PRs. |
| `no_wif_condition_modificaiton.rego` (sic) | Any change to the WIF provider's `attribute_condition`, tightening included |

These resources also have `lifecycle { prevent_destroy = true }`. `.github/CODEOWNERS` names the owner for every path, with explicit entries for `/infra/`, `/.github/`, the orchestrator source and this directory.

## Known gaps

- Installation tokens aren't down-scoped to the job's repository.
- There are no per-installation limits on concurrency or machine size. This is planned.
- All tenants' VMs share one project, one zone and the `default` VPC. Per-tenant isolation is planned.
- The orchestrator's `compute.instanceAdmin.v1` is project-wide.
- `ci-terraform-apply` holds `roles/editor`. This is an explicit exception in `no_basic_roles.rego`.
