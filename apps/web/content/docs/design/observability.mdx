Everything lives in Cloud Logging, Cloud Trace and Cloud Monitoring in the `runnerforge` project. There is no
separate metrics pipeline: the orchestrator writes structured logs, and Terraform turns specific log messages
into **log-based metrics**. SLOs, alert policies and the dashboard are built on those metrics and on Cloud Run's
built-in ones. All of it is Terraform-managed in `infra/terraform/observability_*.tf`.

<Callout type="warn" title="Log messages are an API">
  Metrics match on the exact `message` string (for example `jsonPayload.message="VM creation outcome"`).
  Renaming a message in the orchestrator silently empties the metric, and any alert or SLO built on it. Change
  the message and the filter in `observability_metrics.tf` in the same release.
</Callout>

## Logs

### Format

`logger.py` picks the formatter at startup. On Cloud Run (`K_SERVICE` is set) it uses `JsonFormatter`, which writes
one JSON object per line; Cloud Logging parses it into `jsonPayload`. Locally it uses `ColorFormatter` for
human-readable lines. Every JSON line has:

| Field | Source |
|---|---|
| `severity`, `message`, `timestamp`, `logger` | The Python log record. `severity` becomes the entry's severity. |
| `logging.googleapis.com/sourceLocation` | File, line and function of the log call. |
| `app_version`, `git_sha` | Package version and the first 7 characters of `GIT_SHA`. |
| `logging.googleapis.com/trace`, `logging.googleapis.com/spanId` | Present when the line is written inside an active span. Links the entry to its trace in the console. |
| `exception` | Formatted traceback, when the record has one. |

Request-scoped context comes from a `ContextVar` (`LogContext` in `logger.py`) and is attached to every line written
while it is set: `request_id` (a UUID per HTTP request), and, once a `workflow_job` event passes the label check,
`repo`, `owner`, `sender`, `job_id`, `run_id`, `run_attempt`, `runner_name`, `runner_id`, `installation_id`.
Background tasks (VM creation polling, the preemption check) re-install a snapshot of this context, so their logs
keep the same `request_id`.

The access-log middleware in `main.py` writes one line per request, with message `<METHOD> <path>` (for example
`POST /webhook`) and an `httpRequest` object (`requestMethod`, `requestUrl`, `status`, `latency`, `remoteIp`,
`userAgent`, `protocol`). Cloud Logging promotes it to the entry's `httpRequest`, so filters use
`httpRequest.status`, not `jsonPayload.httpRequest.status`.

<Callout type="info" title="Unhandled exceptions skip the access log">
  If a handler raises, the middleware never writes its line. Uvicorn logs `Exception in ASGI application` at ERROR
  with the traceback in `exception`, and the client gets a 500. The message ends in a newline, so match it with
  `jsonPayload.message:"Exception in ASGI application"`, not `=`. To count 5xx, use Cloud Run's own request log
  (`run.googleapis.com/requests`) or the availability SLO, not `webhook_request_count`.
</Callout>

Startup lines worth knowing: `Resolved runner image` (`image_name`, `image_version`), `Loaded machine types cache`
(`zone`, `count`), `Clients initialized`, and the admission mode. Production admits by the tenant registry
(`ADMISSION=registry`) and logs `Admission by tenant registry` (`allowed_installation_count`), plus the WARNING
`ADMISSION=registry without a registry: only allow-listed installations can create VMs` when the registry is
disabled. Allowlist mode, the default for a self-hosted install without a registry, logs `Installation allow-list
active` (`allowed_installation_count`) or the WARNING `ALLOWED_INSTALLATION_IDS unset: every installation can create
VMs`.
Degraded-mode warnings: `Runner image resolve failed — VMs will boot from family alias` and
`Failed to load machine types cache - validation in degraded mode`.

### Querying

```bash
gcloud logging read '
  resource.type="cloud_run_revision"
  resource.labels.service_name="runnerforge-orchestrator"
  jsonPayload.message="VM creation outcome"
' --project=runnerforge --freshness=1h --limit=50 \
  --format='table(timestamp, jsonPayload.outcome, jsonPayload.error_code, jsonPayload.job_id)'
```

To follow one webhook end to end, filter on its `jsonPayload.request_id`.

### Runner VM logs

The Packer image installs the Cloud Ops Agent (`infra/packer/scripts/install-runner.sh`), and the runner VM service
account has `roles/logging.logWriter`. The startup script tags its lines with `logger -t startup-script`. These land
under `resource.type="gce_instance"`, not under the orchestrator's Cloud Run resource. While a VM still exists,
`gcloud compute instances get-serial-port-output` also shows the boot.

Every VM also starts with `serial-port-logging-enable=TRUE`, so its serial port output reaches Cloud Logging from
boot, and the orchestrator turns it off when the VM's job starts: on the `in_progress` webhook, or from the
reconciler for a VM the webhook missed (`reason: busy`) or a VM past its 10-minute boot window with no recorded job start (`reason: aged`, usually a spare; `busy` when
GitHub says its runner is on a job).
The job's output is the tenant's, so it shouldn't land in Cloud Logging
([ADR-020](/docs/design/decisions#hosted-isolation-a-pool-project-for-tenant-vms)). The
"Serial logging not turned off" alert covers the misses.

## Traces

`tracing.py` enables OpenTelemetry only on Cloud Run. It samples every request (`ALWAYS_ON`), exports to Cloud Trace,
and auto-instruments FastAPI (one server span per request, such as `POST /webhook`) and httpx (one client span per
GitHub API call). Custom spans add the steps:

- `webhook.verify_github_signature`, `webhook.parse_github_response`
- `webhook.handle_queued`, `webhook.handle_in_progress`, `webhook.handle_completed`
- `github.get_installation_token`, `github.get_registration_token`, `github.get_runner`
- `compute.create_vm`, `compute.wait_for_vm_creation`, `compute.delete_vm`, `compute.get_vm_labels_by_job`,
  `compute.get_vm_by_name`, `compute.list_runnerforge_vms`, `compute.active_vm_names`

Handler spans carry `repo`, `sender`, `job_id`, `installation_id`, `labels`, `run_id` and `run_attempt`.

**One trace per runner registration.** `handle_queued` stores the trace and span ID of its `POST /webhook` server
span in the VM's labels (`webhook_trace_id`, `webhook_span_id`). When `in_progress` arrives, `handle_in_progress`
reads those labels and starts its span under that parent, so queued and in_progress show as one trace, with
`webhook.handle_in_progress` next to `webhook.handle_queued`.

**Completion is a separate trace with a link.** The job can run for hours, which would dominate a merged timeline.
`webhook.handle_completed` adds a span link to the queued context instead, so you can jump from a completion to its
registration trace.

If the VM is missing or its labels are malformed, `webhook.handle_in_progress` stays in its own request's trace and the completion gets no link.

| `serial_logging_outcome_count` | counter | `Serial logging outcome` | `outcome`, `trigger`, `reason`, `project_id`, `error_class` |

What the latency metrics measure (from `handlers.handle_in_progress`):

- `runner_readiness_seconds`: GitHub's `started_at` for the job minus the later of the job's `created_at` and the
  time the orchestrator received the `queued` webhook that booted the runner's VM (its `queued_received_at` label).
  The runner's VM is the one in `runner_name`, which after a swap was booted for another job. For the job's own VM
  `created_at` isn't needed. This is the latency on our side.
- A sample whose GitHub timestamps contradict our clock is skipped and logged as `Runner readiness unknown`
  (`reason` and the offsets): `started_at_ahead`, a `started_at` more than 5 s after we received `in_progress`;
  `started_at_before_admission`, a `started_at` more than 5 s before the runner's VM was admitted; or
  `created_at_unusable`, for another job's VM, a `created_at` that is missing or more than 5 s after `started_at` or
  our receipt. On 2026-11-01 GitHub's `created_at` ran an hour ahead of its `started_at`; readiness read 0 s for every
  job until 0.24.1.
- `github_queued_delivery_lag_seconds`: our `queued` receipt time minus the job's `created_at`, only when the
  runner's VM was booted for this job and `created_at` is usable.
- `github_in_progress_delivery_lag_seconds`: our `in_progress` receipt time minus `started_at`.
- `time_to_runner_seconds`: `started_at` minus `created_at`, so it includes GitHub's delivery delay. Not logged when
  it's more than 5 s negative (GitHub's two timestamps disagree).

The first three are floored at zero to absorb clock skew, and are only emitted when the runner's VM still exists at
`in_progress` time and its labels say RunnerForge made it for the same installation.

Things to know when reading them:

- `machine_type` and `image_version` on the two latency metrics are always empty today: the log lines that feed them
  don't carry those fields.
- `runner_vm_count` gets a sample whenever the VMs are listed: every reconciler run (5 minutes) and the daily sweep.
  It's a fleet gauge at 5-minute resolution, not a live one.
- Charts of per-run counts (`runner_vm_count`, `sweep_checked_count`, `sweep_deleted_count`, `sweep_error_count`) use
  `ALIGN_DELTA` with `REDUCE_MEAN`, the exact mean from each distribution's sum and count. A percentile aligner
  estimates within a bucket: with exponential buckets starting at 1, a count of 0 charts as 0.5.
- The `spot` label on the two VM creation metrics was added out of band with `gcloud logging metrics update`, to
  avoid the provider destroying and recreating the metric.
- New log-based metrics take several minutes to become queryable. Dependent SLOs and alerts wait behind
  `time_sleep.wait_for_log_metrics` (120 s). Its `triggers` list every metric name, so adding a metric re-runs the
  sleep instead of only sleeping on the first apply.

## SLOs

Both hang off the `orchestrator` monitoring service (`observability_service.tf`, a `CLOUD_RUN` basic service for
`runnerforge-orchestrator` in `europe-west4`). Defined in `observability_slos.tf`.

| SLO | SLI | Goal | Period |
|---|---|---|---|
| Availability | Cloud Run `basic_sli` availability: 5xx is bad, everything else is good. Covers every route, not only `/webhook`. | 99.5% | Calendar month |
| Time-to-Register | Windows-based on `runner_readiness_seconds`. A 5-minute window is good when at least 99.5% of its samples are ≤ 300 s. | 99.5% of windows | Calendar month |

4xx responses, including HMAC failures and scanner probes, count as good for availability on purpose; the
`webhook_rejection_count` alert covers them instead.

Unless a 5-minute window holds at least 200 registrations, one registration over 300 s is enough to make it bad
(199 of 200 is exactly 99.5%). The metric's exponential buckets have bounds at 256 s and 512 s, so
samples in that range can't be split exactly at 300 s.

## Alert policies

Eleven policies in `observability_alerts.tf`, all sent to one email notification channel, "RunnerForge Alerts"
(`observability_channels.tf`). Only the policy-rejection, job-store, registry-unavailable and serial-logging alerts
have a `documentation` block linking their runbook; for the others, use the runbook column.

| Policy (display name) | Fires when | Severity | Runbook |
|---|---|---|---|
| Availability SLO fast burn (10x over 1h) | Burn rate of the availability SLO over a 1 h lookback > 10. Auto-closes after 30 min. | CRITICAL | [Availability SLO](/docs/guides/runbooks/webhook-availability) |
| Time-to-Register SLO fast burn (10x over 1h) | Burn rate of the time-to-register SLO over a 1 h lookback > 10. Auto-closes after 30 min. | CRITICAL | [Time-to-Register SLO](/docs/guides/runbooks/time-to-register) |
| VM creation failure ratio > 5% (5m) | `failure` + `timeout` outcomes over all outcomes > 0.05, 5-minute alignment, held 5 min | ERROR | [VM creation failures](/docs/guides/runbooks/vm-creation-failures) |
| Lost-webhook ratio &lt; 0.9 (5m) | `queued_outcome_count` over queued `webhook_event_count` below 0.9, 5-minute alignment, held 5 min. Inactive when there's no data. Label-policy rejections, duplicates and admission rejections and deferrals are outcomes, so they don't lower it. | ERROR | [Lost webhooks](/docs/guides/runbooks/lost-webhooks) |
| Every queued job rejected by label policy (1h) | PromQL: ≥ 3 `machine_policy_reject_count` in 1 h `unless` any `vm_creation_count` in that hour. Evaluated every 60 s. | WARNING | [Policy rejection storm](/docs/guides/runbooks/policy-rejections) |
| Job store write failures >= 3 (15m) | More than 2 `job_store_write_failure_count` in a 15-minute window: webhook writes, plus the reconciler's `patch`, `completed`/`in_progress` facts and `delete_by_installation` (the purge after an uninstall, retried each run until it succeeds). `record_fact:vm` and `record_fact:preempted` are excluded from every caller (the reconciler's stuck verdicts included; it retries those), and so are reconciler reads. | WARNING | [Job store write failures](/docs/guides/runbooks/job-store-writes) |
| Queued job rejected: registry unavailable (15m) | Any `queued_rejection_count` with `outcome` `rejected` and `reason` `registry_unavailable` in a 15-minute window. Each is a job lost for good: no record, no redelivery, re-run by hand. Allow-listed installations never read the registry. Auto-closes after 30 min. | WARNING | [Registry unavailable](/docs/guides/runbooks/registry-unavailable) |
| Serial logging not turned off (15m) | Any `serial_logging_outcome_count` with `outcome` `failed`, or with `trigger` `reconcile`, `reason` `busy` and `outcome` `submitted` (the reconciler found a running job's VM still logging), in a 15-minute window. `aged` doesn't count. Auto-closes after 30 min. | WARNING | [Serial logging](/docs/guides/runbooks/serial-logging) |
| Webhook rejections > 5/min (10m) | More than 50 `webhook_rejection_count` in a 10-minute window, held 10 min | WARNING | [Webhook rejections](/docs/guides/runbooks/webhook-rejections) |
| Cold-start latency p95 > 30s (5m) | Cloud Run `container/startup_latencies` p95 > 30 000 ms, 5-minute alignment, held 5 min. Inactive when there's no data. | WARNING | [Cold-start latency](/docs/guides/runbooks/cold-start-latency) |
| Cloud Run instance count > 40 (80% of max=50) | Cloud Run `container/instance_count` max > 40, 1-minute alignment, held 10 min | WARNING | [Instance saturation](/docs/guides/runbooks/instance-saturation) |

A burn rate of 10 means errors are using the monthly budget 10 times faster than sustainable: about 5% bad
requests (or bad windows) over the last hour, which would use a month's budget in about 3 days.

**No sweep liveness alert.** Cloud Monitoring caps an absence condition at 23 h 30 min, and the sweep runs once a
day (Cloud Scheduler job `runnerforge-sweep`, `12 0 * * *` UTC, in `scheduler.tf`), so any absence alert would fire
every night before the sweep. The "Sweep & cleanup" dashboard section is the check instead.

## Dashboard

"RunnerForge — Orchestrator Health", defined in `infra/terraform/dashboards/orchestrator_health.json` and applied by
`observability_dashboards.tf`. If you edit it in the console, run `infra/terraform/sync-dashboards.sh` to export it
back to the JSON, then commit. Sections:

| Section | Panels |
|---|---|
| Orchestrator Health | Request rate by response code class, request latency p50/p95/p99, active instances and cold-start p95 by revision, memory p95 by revision |
| Runner Fleet | VM creation rate by machine type, creation outcomes per minute, deletion rate by reason, active runner VMs, runner readiness p05/p50/p95 |
| Sweep & cleanup | VMs checked, deleted, and errors per sweep run |
| Webhook reliability | Webhook events by `event_type`, lost-webhook ratio |
| Spot & Policy | VM creation rate by spot, preemptions (audit log vs job-confirmed), machine policy rejects by reason |
| Webhook delivery latency | End-to-end time-to-runner p50/p95, GitHub delivery lag p50/p95 |
| Reconciler | Runs per hour (expect 12), stuck / errors / started / orphans deleted per run, job store write failures by operation, queued webhook outcomes by outcome |
| Admission | Queued rejections and deferrals by `outcome` and `reason` |

For how the charts' aligners and reducers work, see [Cloud Monitoring charts](/docs/guides/cloud-monitoring-charts).
