GitHub `workflow_job` webhooks drive the whole runner lifecycle. `POST /webhook` handles every action
(`main.py`). Two backstops cover anything the webhooks miss: a daily sweep (`sweep.py`) and a runtime cap that
GCE enforces on every VM.

## Every request

<Steps>
  <Step>
    **Signature.** The orchestrator computes an HMAC-SHA256 of the raw body with the webhook secret and
    compares it to `X-Hub-Signature-256` in constant time. A mismatch returns **401**. A request missing
    `X-Hub-Signature-256` or `X-GitHub-Event` is rejected with **422** before this check.
  </Step>
  <Step>
    **Event type.** The orchestrator dispatches on the `X-GitHub-Event` header, not on the payload's shape.
    Anything other than `workflow_job` (`ping`, `installation`, `installation_repositories`, …) gets a
    **200** and is ignored.
  </Step>
  <Step>
    **Parse.** A body that isn't JSON returns **400**. A body that doesn't match the `WorkflowJobEvent`
    model returns **500**, because that usually means GitHub changed its payload.
  </Step>
  <Step>
    **RunnerForge filter.** A job with no `runnerforge` label (case-insensitive) gets a **200** and nothing
    else happens. This keeps traffic for GitHub-hosted runners and your other runners cheap.
  </Step>
  <Step>
    **Allow-list (`queued` only).** If `ALLOWED_INSTALLATION_IDS` is set and doesn't contain the event's
    installation, the orchestrator logs `Installation not allowed` and returns **200**. No VM is created.
  </Step>
  <Step>
    **Accepted.** The orchestrator logs `Webhook event received` with `event_type`. This comes after the
    gate on purpose, so rejected installations don't count toward the lost-webhook alert.
  </Step>
</Steps>

## Queued

<Steps>
  <Step>
    **Resolve labels** to a machine type and spot flag (see [Label parsing](#label-parsing)). A rejected
    label set logs `Machine policy rejected` with a `reason` and returns 200 with no VM.
  </Step>
  <Step>
    **Get a registration token.** The App JWT is exchanged for an installation token. That token then
    mints a registration token for the repo. Calls that hit network errors or 5xx responses are tried up to 3 times.
  </Step>
  <Step>
    **Create the VM** named `runnerforge-{run_id}-{job_id}-{run_attempt}`. Its metadata holds the token,
    the repo URL and the job's labels. The VM's own labels identify it (see
    [Architecture](/docs/design/architecture#runner-vms)). The call submits the insert and doesn't wait.
  </Step>
  <Step>
    **Return 200.** A background task polls the GCE operation for up to 300 s and logs `VM creation outcome`
    (`success`, `failure` or `timeout`).
  </Step>
</Steps>

The VM's startup script then mounts the data disk, runs `config.sh --ephemeral` with the VM name as the
runner name, and starts the runner. The runner registers with GitHub, and GitHub assigns it a matching
queued job.

<Callout type="warn" title="A rejected job stays queued">
  When the allow-list or the label policy rejects a job, GitHub still shows it as queued. Unless another
  of your runners matches its labels, no runner will come, and the job waits until GitHub's own queue
  timeout fails it.
</Callout>

### Label parsing

`machine_policy.resolve_labels` runs on the job's `runs-on` labels, case-insensitively:

| Label | Effect |
| --- | --- |
| `runnerforge` | Required. Routes the job to RunnerForge. |
| `self-hosted`, `linux`, `x64` | Accepted and ignored. GitHub adds these to every runner we boot. |
| `spot` | Use a Spot VM. |
| `small` / `medium` / `large` / `xlarge` | `n2-standard-2` / `-4` / `-8` / `-16` |
| A literal GCE type, such as `e2-standard-4` | Used as is if it exists in the zone, checked against a list cached at startup. Otherwise rejected (`invalid_machine_type`). If the list failed to load, the type is passed through and GCE rejects a bad one on insert. |
| No size label | `n2-standard-4` |
| Two machine labels | Rejected (`conflicting_machines`) |
| Anything else not shaped like a machine type, including `windows`, `macos`, `arm64` | Rejected (`unknown_token`) |

### Duplicates and re-runs

The VM name is deterministic. If a `queued` event is delivered twice, for example redelivered by hand from
the App's delivery log, the second insert fails with `AlreadyExists`. The orchestrator logs `VM already exists` and creates no second VM.
A re-run of the job has a new `run_attempt`, so it gets a new name and a new VM.

## In progress

There is no VM action. The orchestrator finds the VM booted for this job by its `job_id`, `run_id` and
`run_attempt` labels, then:

- parents this request's trace under the queued request's trace, so registration shows up as one trace;
- logs `Runner registration outcome` with `runner_readiness_seconds`, the time from receiving the queued
  webhook to the job starting. This is the source of the time-to-register SLO.

## Completed

`completed` covers every way a job ends; the `conclusion` field (`success`, `failure`, `cancelled`, …)
says which. The orchestrator
deletes the VM named by the event's `runner_name`, which is the VM that actually ran the job. Before
deleting, it checks:

<Steps>
  <Step>
    **There is a runner.** A job cancelled before any runner picked it up has no `runner_name`. There is
    nothing to delete. The sweep or the runtime cap removes the VM that was booted for it.
  </Step>
  <Step>
    **The name has the `runnerforge-` prefix.** Otherwise it's one of your own runners, so it's skipped
    quietly.
  </Step>
  <Step>
    **The VM exists.** If it's already gone (GCE deletes preempted Spot VMs itself), nothing is deleted, but the
    preemption cross-check below still runs.
  </Step>
  <Step>
    **The VM is ours and belongs to this installation.** Whoever registers a runner chooses its name, so the
    prefix alone proves nothing. The VM's labels must say `runner=runnerforge`, and its `installation_id`
    must equal the event's installation. If they don't, the orchestrator logs
    `Refusing to delete VM not owned by this installation` and leaves the VM alone.
  </Step>
</Steps>

After the delete is submitted, a `failure` or `cancelled` conclusion starts a background audit-log check for
Spot preemption.

### Job swaps

A runner takes **any** queued job in its repo whose labels match, not only the job it was booted for. VM X,
booted for job X, may run job Y while job X runs on VM Y. Webhook cleanup still works because it deletes by
`runner_name`, the VM that actually ran the job. Labels like `job_id` record why a VM was booted, not which
job it ran.

<Callout type="warn" title="Known gap: the sweep and swapped jobs">
  The sweep checks the job a VM was booted for (`job_id` label), not the job it is running. Suppose VM X is over
  an hour old and still running job Y, and job X has already finished on another VM. A sweep at that moment
  deletes VM X in the middle of job Y.
</Callout>

## Sweep

Cloud Scheduler job `runnerforge-sweep` calls `POST /sweep` daily at **00:12 UTC** (`scheduler.tf`) with an
OIDC token. The orchestrator verifies the token's audience and its service-account email. It lists VMs
labelled `runner=runnerforge` and skips any whose labels don't parse. For each remaining VM:

| Age / state | Decision |
| --- | --- |
| Younger than 1 h | Skip (`too_young`). The webhooks should handle it. |
| Older than 6 h 15 min (`MAX_VM_RUN_DURATION`) | Delete (`hard_limit`), whatever the job status. |
| `repo-url` metadata missing or not a `https://github.com/` URL | Skip (`unknown_repo`). The hard limit still applies later. |
| GitHub says the job is `completed`, or returns 404 | Delete (`job_completed`) |
| Otherwise | Skip (`job_running`) |

The repo comes from the VM's `repo-url` metadata, never from labels. GCE label values are lowercase and at
most 63 characters, so they can't hold an exact `owner/repo`. Asking GitHub about a guessed repo would get a
404, which reads as "orphan". If one VM fails, the error is recorded and the sweep moves on to the next. The
response reports `checked`, `deleted`, `skipped` and `errors`.

## Runtime cap

Every VM is created with `max_run_duration` = 6 h 15 min and termination action `DELETE`. GCE deletes the VM
and its disks even if both the webhook and the sweep miss it. That is GitHub's default 6 h job timeout plus
15 min for boot and registration.

## What isn't recovered

GitHub doesn't retry failed webhook deliveries.

- **A lost `queued` webhook** means no VM is created, and nothing recreates it. The job waits until GitHub's
  queue timeout. The `lost_webhook_ratio` alert only catches queued webhooks that were accepted but produced
  no VM creation (label-policy rejections and duplicates count here too), not ones that never arrived.
- **A lost `completed` webhook** leaves the VM running. The first sweep after the VM is 1 h old deletes it if its
  job is done. Otherwise the runtime cap deletes it.

## Concurrency

Each Cloud Run instance handles up to 10 requests at once, and the service scales to 50 instances. No job
state lives in the orchestrator process (only API clients and startup caches); the only shared job state
is GCE itself. Simultaneous jobs with the same labels each get their
own VM, and GitHub hands the runners out to queued jobs, which is where swaps come from.
