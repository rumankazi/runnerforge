GitHub `workflow_job` webhooks drive the whole runner lifecycle. `POST /webhook` handles every action
(`main.py`). Three backstops cover VMs the webhooks miss: the reconciler's [orphan cleanup](#orphan-cleanup)
every 5 minutes, a daily sweep (`sweep.py`), and a runtime cap that GCE enforces on every VM.

## Every request

<Steps>
  <Step>
    **Signature.** The orchestrator computes an HMAC-SHA256 of the raw body with the webhook secret and
    compares it to `X-Hub-Signature-256` in constant time. A mismatch returns **401**. A request missing
    `X-Hub-Signature-256` or `X-GitHub-Event` is rejected with **422** before this check.
  </Step>
  <Step>
    **Event type.** The orchestrator dispatches on the `X-GitHub-Event` header, not on the payload's shape.
    `installation` events (`created`, `deleted`, `suspend`, `unsuspend`) update the tenant registry: a new
    installation gets a `pending` row (see [ADR-019](/docs/design/decisions#tenant-registry-install-to-register-admin-approval-per-installation-limits)).
    Anything else other than `workflow_job` (`ping`, `installation_repositories`, …) gets a **200** and is
    ignored.
  </Step>
  <Step>
    **Parse.** A body that isn't JSON returns **400**. A body that doesn't match the `WorkflowJobEvent`
    model returns **500**, because that usually means GitHub changed its payload.
  </Step>
  <Step>
    **RunnerForge filter.** A job with no `runnerforge` label (case-insensitive) gets a **200** and nothing
    else happens. This keeps traffic for GitHub-hosted runners and your other runners cheap.
  </Step>
  <Step>
    **Allow-list (`queued` only).** If `ALLOWED_INSTALLATION_IDS` is set and doesn't contain the event's
    installation, the orchestrator logs `Installation not allowed` and returns **200**. No VM is created.
  </Step>
  <Step>
    **Accepted.** The orchestrator logs `Webhook event received` with `event_type`. This comes after the
    gate on purpose, so rejected installations don't count toward the lost-webhook alert.
  </Step>
</Steps>

## Queued

<Steps>
  <Step>
    **Create the job record** in Firestore ([ADR-018](/docs/design/decisions#per-job-state-in-firestore-behind-a-jobstore-protocol)).
    If a closed record already exists, `completed` arrived first: the orchestrator logs the outcome
    `already_completed` and creates no VM.
  </Step>
  <Step>
    **Resolve labels** to a machine type and spot flag (see [Label parsing](#label-parsing)). A rejected
    label set logs `Machine policy rejected` with a `reason`, records the decision, and returns 200 with no VM.
  </Step>
  <Step>
    **Get a registration token.** The App JWT is exchanged for an installation token. That token then
    mints a registration token for the repo. Calls that hit network errors or 5xx responses are tried up to 3 times.
  </Step>
  <Step>
    **Create the VM** named `runnerforge-{run_id}-{job_id}-{run_attempt}`. Its metadata holds the token,
    the repo URL and the job's labels. The VM's own labels identify it (see
    [Architecture](/docs/design/architecture#runner-vms)). The call submits the insert and doesn't wait.
  </Step>
  <Step>
    **Return 200.** A background task polls the GCE operation for up to 300 s, logs `VM creation outcome`
    (`success`, `failure` or `timeout`) and records it on the job.
  </Step>
</Steps>

If the token fetch or the GCE insert fails, the orchestrator records an `errored` fact with that stage and
returns 500.

<Callout type="info" title="Job records never block a job">
  Every store call is bounded at 2 s and fails open: a slow or broken store logs `Job store write failed`
  and the webhook carries on. If the first call on a `queued` request fails, that request skips its other
  writes, so a degraded store adds at most about 4 s. Records are written only for installations on the
  allow-list, for every action.
</Callout>

The VM's startup script then mounts the data disk, runs `config.sh --ephemeral` with the VM name as the
runner name, and starts the runner. The runner registers with GitHub, and GitHub assigns it a matching
queued job.

<Callout type="warn" title="A rejected job stays queued">
  When the allow-list or the label policy rejects a job, GitHub still shows it as queued. Unless another
  of your runners matches its labels, no runner will come, and the job waits until GitHub's own queue
  timeout fails it.
</Callout>

### Label parsing

`machine_policy.resolve_labels` runs on the job's `runs-on` labels, case-insensitively:

| Label | Effect |
| --- | --- |
| `runnerforge` | Required. Routes the job to RunnerForge. |
| `self-hosted`, `linux`, `x64` | Accepted and ignored. GitHub adds these to every runner we boot. |
| `spot` | Use a Spot VM. |
| `small` / `medium` / `large` / `xlarge` | `n2-standard-2` / `-4` / `-8` / `-16` |
| A literal GCE type, such as `e2-standard-4` | Used as is if it exists in the zone, checked against a list cached at startup. Otherwise rejected (`invalid_machine_type`). If the list failed to load, the type is passed through and GCE rejects a bad one on insert. |
| No size label | `n2-standard-4` |
| Two machine labels | Rejected (`conflicting_machines`) |
| Anything else not shaped like a machine type, including `windows`, `macos`, `arm64` | Rejected (`unknown_token`) |

### Duplicates and re-runs

The VM name is deterministic. If a `queued` event is delivered twice, for example redelivered by hand from
the App's delivery log, the second insert fails with `AlreadyExists`. The orchestrator logs `VM already exists` and creates no second VM.
A re-run of the job has a new `run_attempt`, so it gets a new name and a new VM.

## In progress

There is no VM action. GitHub gives a queued job to any idle runner with matching labels, so the VM running the
job can be one booted for another job. The orchestrator reads the VM named in `runner_name`, if its labels say
RunnerForge made it for the same installation (without a `runner_name`, the VM booted for this job, found by its
`job_id`, `run_id` and `run_attempt` labels), then:

- parents this request's trace under the trace of the queued request that booted that VM;
- logs `Runner registration outcome` with `runner_readiness_seconds`, to the job starting: from the VM's admission
  (its `queued_received_at` label) when the VM was booted for this job, otherwise from the later of that admission
  and the job's `created_at`. When GitHub's timestamps
  contradict our clock, the sample is skipped and `Runner readiness unknown` is logged instead. A swapped VM then isn't slow
  registration, and an idle VM left by a cancelled job counts as ready at once. This is the source of the
  time-to-register SLO.

## Completed

`completed` covers every way a job ends; the `conclusion` field (`success`, `failure`, `cancelled`, …)
says which. The orchestrator
deletes the VM named by the event's `runner_name`, which is the VM that actually ran the job. Before
deleting, it checks:

<Steps>
  <Step>
    **There is a runner.** A job cancelled before any runner picked it up has no `runner_name`. There is
    nothing to delete. The reconciler's [orphan cleanup](#orphan-cleanup) deletes the VM that was booted for it
    once it is 15 minutes old; the sweep and the runtime cap back that up.
  </Step>
  <Step>
    **The name has the `runnerforge-` prefix.** Otherwise it's one of your own runners, so it's skipped
    quietly.
  </Step>
  <Step>
    **The VM exists.** If it's already gone (GCE deletes preempted Spot VMs itself), nothing is deleted, but the
    preemption cross-check below still runs.
  </Step>
  <Step>
    **The VM is ours and belongs to this installation.** Whoever registers a runner chooses its name, so the
    prefix alone proves nothing. The VM's labels must say `runner=runnerforge`, and its `installation_id`
    must equal the event's installation. If they don't, the orchestrator logs
    `Refusing to delete VM not owned by this installation` and leaves the VM alone.
  </Step>
</Steps>

After the delete is submitted, a `failure` or `cancelled` conclusion starts a background audit-log check for
Spot preemption.

### Job swaps

A runner takes **any** queued job in its repo whose labels match, not only the job it was booted for. VM X,
booted for job X, may run job Y while job X runs on VM Y. Webhook cleanup still works because it deletes by
`runner_name`, the VM that actually ran the job. Labels like `job_id` record why a VM was booted, not which
job it ran. For the same reason the sweep asks GitHub about the runner on the VM, never about the job the VM
was booted for.

## Sweep

Cloud Scheduler job `runnerforge-sweep` calls `POST /sweep` daily at **00:12 UTC** (`scheduler.tf`) with an
OIDC token. The orchestrator verifies the token's audience and its service-account email. It lists VMs
labelled `runner=runnerforge` and skips any whose labels don't parse. For each remaining VM:

| Age / state | Decision |
| --- | --- |
| Younger than 1 h | Skip (`too_young`). The webhooks should handle it. |
| Older than 6 h 15 min (`MAX_VM_RUN_DURATION`) | Delete (`hard_limit`), whatever the job status. |
| `repo-url` metadata missing or not a `https://github.com/` URL | Skip (`unknown_repo`). The hard limit still applies later. |
| The repo returns 404 (deleted, or no longer visible to the App) | Skip (`repo_not_found`). No evidence either way; the hard limit still applies. |
| A runner named like the VM is registered and `busy` | Skip (`runner_busy`), whichever job it is running. |
| A runner named like the VM is registered but idle | Delete (`runner_idle`). Its job went to another runner. |
| No runner by that name | Delete (`runner_gone`). Runners are `--ephemeral`, so GitHub de-registers them after their one job. |

The sweep looks the runner up with `GET /repos/{owner}/{repo}/actions/runners?name=<vm name>` and matches the
name exactly. The repo comes from the VM's `repo-url` metadata, never from labels. GCE label values are
lowercase and at most 63 characters, so they can't hold an exact `owner/repo`. If one VM fails, the error is recorded and the sweep moves on to the next. The
response reports `checked`, `deleted`, `skipped` and `errors`.

## Reconciler

Cloud Scheduler calls `POST /reconcile` every 5 minutes with the same OIDC identity as the sweep. It brings
open job records ([ADR-018](/docs/design/decisions#per-job-state-in-firestore-behind-a-jobstore-protocol)) in
line with GitHub and GCE, for what the webhooks and background tasks missed. The only VMs it deletes are
orphans. Each run:

1. Takes up to 25 open records whose next check is due, earliest first.
2. Lists RunnerForge VMs once. A VM whose job has no open record gets one, built from its labels and metadata.
3. Runs the **orphan cleanup** (below); no new check starts after 30 s.
4. With `ADMISSION=registry`, runs the **capacity pass** (below), in its own 40 s.
5. For each record: one already holding `completed` is closed. Otherwise it asks GitHub
   (`GET /repos/{owner}/{repo}/actions/jobs/{job_id}`):

| GitHub says | Reconciler |
| --- | --- |
| `completed` | Records the conclusion and runner, and closes the record. |
| 404, or the App installation is gone | Records `conclusion: gone` and closes the record. |
| `in_progress` | Records the runner if missing. |
| Still queued, and its own VM exists and isn't running another job | Records `vm: success` if the watcher never did. |
| Still queued, own VM gone (or running another job), no other VM can take it | Records `preempted: before_pickup` if the audit log names its VM, otherwise `vm: missing`. The dashboard shows it as stuck. If the audit log can't answer, it records nothing and asks again next time. A limited tenant's job with reconciler starts left waits for the capacity pass instead. |
| Still queued, another VM could take it | Waits. A VM can take it if it's for the same repository, isn't running another job, and its labels cover the job's. |

Every record it doesn't close is checked again after a backoff: 5 min, 15 min, 1 h, then every 6 h. Rejected,
errored and running jobs start at 1 h. One failing record is logged and retried later; it doesn't stop the run.
A run stops starting records after 120 s (each record is bounded at 30 s) and reports `more_due`; the rest wait
for the next run. The run logs `Reconcile completed` with its counts.

"Its own VM" is the one last made for the job: the decision's `vm_name` after a reconciler start, otherwise
`runnerforge-{run}-{job}-{attempt}`.

### Orphan cleanup

A VM is deleted only on its job's `completed` webhook, so a VM whose runner never gets a job keeps running: its job
was cancelled before pickup or ran on another runner, or its `completed` webhook was lost. Under a tenant's limit it
also holds a slot. Every run, in both admission modes, the reconciler asks GitHub about the runner on each such VM
(`GET /repos/{owner}/{repo}/actions/runners?name={vm_name}`; VM name = runner name):

- **Which VMs:** PROVISIONING, STAGING or RUNNING, over 15 minutes old (past the spare window below), with a known
  repository, of an installation that gets job records (allow-listed, or approved at least once; every installation
  when the allow-list is unset in allowlist mode). Not one GitHub has suspended, since GitHub refuses its calls. An
  installation the owner suspended is checked: its idle runners could still take new jobs.

| GitHub says | Cleanup |
| --- | --- |
| No runner of that name | Deletes the VM. An ephemeral runner leaves the list after its one job, or never registered. This holds even if a record still says the VM is busy, which a lost `completed` webhook leaves behind. |
| Busy, or a record's `in_progress` names the VM | Keeps it. GitHub's busy flag can read false mid-job, so the records back it up. |
| Idle and online, and a job of the installation is waiting in the same repository with labels it covers | Keeps it: GitHub would hand it that job. |
| Idle otherwise | Deregisters the runner (`DELETE /repos/{owner}/{repo}/actions/runners/{id}`), so GitHub can't hand it a job while the VM shuts down, then deletes the VM. |
| The repository is gone (404), or any error | Keeps it. The runtime cap still removes it. |

- **Fails closed:** if the open-records read failed, or returned the full 500 (it may have left out a busy runner's
  record), the cleanup is skipped for the run.
- **Bounds:** 10 checks a run, 15 s each, and no new check after 30 s, in a different order each run so VMs kept
  every run (long jobs) can't always take the checks. A failed check is logged and the VM kept; it doesn't stop the
  run.
- **After a delete:** the VM is left out of the rest of the run, so the capacity pass can use its slot at once (a
  live listing that still shows it doesn't count it). The cleanup writes nothing on job records. A job whose own VM
  it was is left to the batch, which asks GitHub first: a runner gone from GitHub usually ran its job, even when the
  webhooks that would say so were lost. `Reconcile completed` reports `orphans_deleted`; each delete logs
  `Orphan VM deleted`. A VM GCE no longer has (its `completed` webhook got there first) isn't counted.

GitHub documents the runner `DELETE` as a forced removal. A job GitHub hands the runner in the moment between the
check and the deregistration is lost with the VM.

### Capacity pass

With `ADMISSION=registry` ([ADR-019](/docs/design/decisions#tenant-registry-install-to-register-admin-approval-per-installation-limits)),
the reconciler starts VMs for jobs waiting under an installation's limit. GitHub gives a queued job to any idle
runner with matching labels, so it works from free slots, not from decision kinds.

- **Installations:** every one approved at least once, plus the allow-list. One that's no longer admitted gets its
  deferred jobs marked `rejected` with the reason. If the registry can't be read, the installation is skipped for
  the run, not rejected, and its stuck verdicts wait too.
- **Free slots:** `max_concurrent_vms` minus the installation's PROVISIONING, STAGING or RUNNING VMs, counted live,
  leaving out the VMs the orphan cleanup just deleted.
  Unlimited installations (limits lifted, or allow-listed) are bounded only by the run's cap.
- **Waiting jobs**, oldest first from that installation's open records (up to 100): deferred jobs; and, for a
  limited installation, jobs whose VM is gone, dead or running another job (not within 3 minutes of their
  decision). Not jobs queued over 23.5 h, nor ones with 2 reconciler starts already.
- **Each one:** it asks GitHub for the job. One that's no longer queued gets its fact and is left. A VM of the same
  installation and repository that is up, not on a job, under 15 minutes old and has covering labels can still
  take it, so it waits; each such VM excuses one job. A job its limits now reject is marked `rejected`
  (`limit_size`).
- **A start** first claims the record with a conditional write: only if it has no `in_progress` or `completed`
  and nobody started it since it was read. The claim writes `decision {kind: vm_submitted, source: reconcile,
  start, vm_name}`, clears the last attempt's `vm`, `preempted` and `errored`, and resets the backoff. The VM is
  then created by the same code as the webhook path, with `queued_received_at` set to now and the run's installation
  token, and a watcher records its `vm` fact as on the webhook path. Its name is the base name for a job that never
  had a VM, otherwise `-r{start}`; names are never reused.
- **Capacity errors:** a start whose operation failed with `QUOTA_EXCEEDED` or `ZONE_RESOURCE_POOL_EXHAUSTED`
  isn't counted against the job: the next start reuses its number and name (GCE never made that VM), up to 3
  times per job. The watcher's `vm` fact names its VM, so only a failure of the latest start counts. While such a
  failure is under 10 minutes old, a quota error pauses every start and a stockout pauses only that machine type.
- **Bounds:** 10 starts a run, 3 GitHub lookups per free slot, 15 s per start, one start per installation per
  round. A failed start ends that installation's turn for the run; a quota or zone-capacity error ends the pass.
  A slot is counted from the claim, so a start cancelled mid-insert still holds one. `Reconcile completed` reports
  `started`.

## Runtime cap

Every VM is created with `max_run_duration` = 6 h 15 min and termination action `DELETE`. GCE deletes the VM
and its disks even if both the webhook and the sweep miss it. That is GitHub's default 6 h job timeout plus
15 min for boot and registration.

## What isn't recovered

GitHub doesn't retry failed webhook deliveries.

- **A lost `queued` webhook** means no VM is created, and nothing recreates it. The job waits until GitHub's
  queue timeout. The `lost_webhook_ratio` alert only catches queued webhooks that were accepted but never
  reached a decision (no `Queued webhook outcome` line, e.g. a token error), not ones that never arrived.
  Label-policy rejections and duplicates are decisions and don't lower the ratio.
- **A lost `completed` webhook** leaves the VM running. Once the VM is 15 minutes old, the reconciler's
  [orphan cleanup](#orphan-cleanup) sees its runner gone from GitHub and deletes it. The daily sweep and the runtime
  cap back that up.

## Concurrency

Each Cloud Run instance handles up to 10 requests at once, and the service scales to 50 instances. No job
state lives in the orchestrator process (only API clients and startup caches); the only shared job state
is GCE itself. Simultaneous jobs with the same labels each get their
own VM, and GitHub hands the runners out to queued jobs, which is where swaps come from.
