RunnerForge gives GitHub Actions jobs a fresh GCE VM each. A GitHub App sends `workflow_job` webhooks to a
FastAPI orchestrator on Cloud Run. The orchestrator boots a VM from a Packer-built image for each queued job
that asks for `runnerforge`, and deletes it when the job completes. Terraform owns everything else.

<Callout type="info" title="Who can use it today">
  The GitHub App is private. Only installations on the orchestrator's allow-list get VMs. A free hosted
  beta with manual approval is planned; see [Status](#status).
</Callout>

## Requirements

- A queued job whose `runs-on` includes `runnerforge` gets its own fresh VM, used for one job only.
- The job's labels pick the machine: a size (`small` to `xlarge`) or a literal GCE machine type, plus
  optional `spot`. See [label parsing](/docs/design/webhook-flow#label-parsing).
- The VM is deleted when the job completes. If that delete is missed, the daily sweep or GCE's own
  runtime cap removes it.
- Only allow-listed GitHub App installations can create VMs. An installation is one GitHub user or
  organization, and it is the unit of tenancy.
- The orchestrator sees job events and mints runner registration tokens. It never reads repository
  contents; your job's code runs only on the job's own VM. See [Trust & threat model](/docs/design/trust).
- Planned: users see their own usage on the website, and admins see usage per installation.

<Callout type="warn" title="Open question">
  Per-installation usage metrics for admins need a legal review before implementation: confirm what we
  can collect and show without explicit user consent.
</Callout>

## Constraints

- Provisioning is on-demand only, with no warm pool. See ADR-005 in [Decisions](/docs/design/decisions).
- No always-on compute: Cloud Run scales to zero (`min_instance_count = 0`) and VMs are created only for
  queued jobs. See [Cost when idle](/docs/design/architecture#cost-when-idle).
- VM state lives on the VM itself, in labels and metadata (ADR-004). Each job's history is a record in
  Firestore, written fail-open so a store problem never blocks a job (ADR-018).
- The runner image ships through its own automated pipeline (`deploy-runner-image.yaml`): build, smoke
  test, promote to the image family, keep the five newest images active.

## Acceptance criteria

These are the SLOs and alerts codified in Terraform, not aspirations.

| Criterion | Target | Source |
| --- | --- | --- |
| Availability | 99.5% of requests are non-5xx, per calendar month. 4xx (bad signatures, scanners) counts as good. | `observability_slos.tf` → `availability` |
| Time to register | 99.5% of 5-minute windows in a calendar month have at least 99.5% of runners picking up their job within 300 s of RunnerForge receiving the queued webhook (`runner_readiness_seconds`). | `observability_slos.tf` → `time-to-register` |
| No lost work | Alert when queued webhooks that reached a decision (`queued_outcome_count`: VM submitted, duplicate, or label rejection) divided by accepted queued webhooks (`webhook_event_count`, `event_type=queued`) stays below 0.9 for 5 minutes. | `observability_alerts.tf` → `lost_webhook_ratio` |
| No orphaned VMs | No VM runs longer than 6 h 15 min. GCE deletes it, and the sweep backs that up. | `compute_client.MAX_VM_RUN_DURATION` |

**Next (planned, no dates):**

1. Docs and website refresh.
2. Tenant registry: a record per installation that holds its approval and its limits.
3. Hosted isolation: stronger separation between different tenants' runner VMs.
4. Usage tracking per installation, to enforce those limits.
5. User-facing dashboard.
