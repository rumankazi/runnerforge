How to check current GCP quotas, which ones limit how many runners RunnerForge can run at once, and how to raise them.

<Callout type="info" title="Quota changes go through Terraform">
  RunnerForge's quota preferences are declared in [`infra/terraform/quotas.tf`](https://github.com/rumankazi/runnerforge/blob/main/infra/terraform/quotas.tf). To change one, edit its `preferred_value` and open a PR; CI plans and applies it. Use the `gcloud` commands below to look up quotas, or for a new quota that isn't in Terraform yet: create it with `gcloud`, then `terraform import` it into `quotas.tf`.
</Callout>

## Background — two quota APIs

GCP exposes quotas through two generations of tooling. Both are still live; they surface partially-overlapping data.

| API | Command prefix | Notes |
|---|---|---|
| **Legacy** | `gcloud compute regions describe <region>` | Familiar, but the metric names (`E2_CPUS`, `INSTANCES`) are legacy. Some entries are phantoms with no adjustable equivalent in the new system. |
| **Cloud Quotas (current)** | `gcloud alpha quotas …` | Source of truth for what's adjustable today. Use this for any *request* flow. |

When the legacy command shows a quota the new API doesn't expose as separately adjustable, trust the new API — the legacy display can be stale.

## Check a single quota

```bash
gcloud alpha quotas info describe <QUOTA_ID> \
  --service=<SERVICE> \
  --project=runnerforge \
  --format="json" | jq '.dimensionsInfos[] | select(.dimensions.region == "europe-west4")'
```

Common service IDs:
- `compute.googleapis.com` — VMs, CPUs, IPs, disks, NAT
- `run.googleapis.com` — Cloud Run services, revisions
- `artifactregistry.googleapis.com` — repositories, image storage
- `logging.googleapis.com` — log-based metrics, retention
- `monitoring.googleapis.com` — dashboards, alert policies

Example — check current `INSTANCES` limit in europe-west4:

```bash
gcloud alpha quotas info describe INSTANCES-per-project-region \
  --service=compute.googleapis.com \
  --project=runnerforge \
  --format="json" \
  | jq '.dimensionsInfos[] | select(.dimensions.region == "europe-west4") | .details.value'
```

## List all quotas for a service (find the right ID)

```bash
gcloud alpha quotas info list \
  --service=compute.googleapis.com \
  --project=runnerforge \
  --format="value(quotaId)" \
  | grep -i "<search term>"
```

Examples:

```bash
# Find all CPU-related quota IDs
gcloud alpha quotas info list --service=compute.googleapis.com \
  --project=runnerforge --format="value(quotaId)" | grep -i cpu

# Find network-related quota IDs
gcloud alpha quotas info list --service=compute.googleapis.com \
  --project=runnerforge --format="value(quotaId)" | grep -iE "network|address|nat"
```

## Request an increase

```bash
gcloud alpha quotas preferences create \
  --service=<SERVICE> \
  --project=runnerforge \
  --quota-id=<QUOTA_ID> \
  --dimensions=region=<REGION> \
  --preferred-value=<NEW_LIMIT> \
  --email=<CONTACT_EMAIL> \
  --justification="<reason>"
```

Example — bump `INSTANCES` to 200 in europe-west4:

```bash
gcloud alpha quotas preferences create \
  --service=compute.googleapis.com \
  --project=runnerforge \
  --quota-id=INSTANCES-per-project-region \
  --dimensions=region=europe-west4 \
  --preferred-value=200 \
  --email=<CONTACT_EMAIL> \
  --justification="Self-hosted CI runner platform"
```

`INSTANCES` is already at 200 in `quotas.tf`; this is the command shape that was used before it was imported.

## Verify approval

```bash
gcloud alpha quotas preferences list --project=runnerforge
```

Look at the most recent entry:

```yaml
quotaConfig:
  grantedValue: '200'
  preferredValue: '200'
```

- `grantedValue` equals `preferredValue` → the new limit is in effect.
- `grantedValue` is lower → the request is still in review or was partly or fully denied. Read `stateDetail`, and watch the contact email for questions from Google.

## Quotas that bind RunnerForge

The size labels map to `n2-standard-*` machine types (`machine_policy.py`: `small`=2, `medium`=4 (the default), `large`=8, `xlarge`=16 vCPUs). A literal machine-type label, such as `e2-standard-4`, uses that family's CPU quota instead. Each VM gets a 50 GB `pd-balanced` data disk, which counts against SSD quota, and a 10 GB boot disk with no disk type set (`compute_client.py`). Values below are for `europe-west4`, from the capacity notes in `quotas.tf` (checked 2026-06-12, not live).

| Quota | Value | Source | What it gates |
|---|---|---|---|
| `INSTANCES-per-project-region` | 200 | Requested, in `quotas.tf` | Concurrent VMs |
| `SSD-TOTAL-GB-per-project-region` | 1500 | Requested, in `quotas.tf` | Total SSD-backed disk: 30 concurrent runners at 50 GB of data disk each. **The binding limit for `small` and `medium`** |
| `N2_CPUS` | 200 | GCP default | N2 vCPUs, for both on-demand and Spot VMs. **Binds before SSD for `large`** (25 concurrent) **and `xlarge`** (12 concurrent) |
| `E2_CPUS` | 24 | GCP default | E2 vCPUs, used by literal `e2-*` labels. Too small to be the default runner family |
| `CPUS` | 200 | GCP default | N1 only in modern regions; doesn't gate E2 or N2 |
| `N2D_CPUS` | 16 | GCP default | N2D vCPUs, used by literal `n2d-*` labels |

<Callout type="info" title="Spot VMs don't use PREEMPTIBLE_CPUS">
  Spot VMs (`provisioning_model = SPOT`) count against the machine family's CPU quota, such as `N2_CPUS`. `PREEMPTIBLE_CPUS` applies only to legacy preemptible VMs, which RunnerForge doesn't create. A leftover `PREEMPTIBLE_CPUS` preference exists in the project and is deliberately not in Terraform; it gates nothing.
</Callout>

Runner VMs have no external IP (egress goes through Cloud NAT, `network.tf`), so `IN-USE-ADDRESSES` doesn't scale with runners.

## When to bump what (RunnerForge-specific guidance)

- **More concurrent `small` or `medium` runners**: raise `SSD-TOTAL-GB` first; it binds at 30 VMs. Then check `N2_CPUS` (200) and `INSTANCES` (200) against the new ceiling: 30 `medium` runners already use 120 of the 200 N2 vCPUs.
- **Heavy use of `large` or `xlarge`**: `N2_CPUS` binds first (8 or 16 vCPUs each). Raise it alongside `SSD-TOTAL-GB`.
- **Adopting another machine family**: raise that family's CPU quota (for example `N2D_CPUS`), for on-demand and Spot alike.

## Console route (fallback)

If the gcloud commands fail (alpha API instability, permission edge case), use the GCP Console:

1. Navigate to **IAM & Admin → Quotas & System Limits**
2. Filter by metric name (e.g., `INSTANCES`) or service (e.g., `Compute Engine API`)
3. Tick the row for the right region
4. Click **Edit quotas**
5. Enter new limit + justification, submit

The Console uses the same Cloud Quotas backend, so approval timing is identical.

## Quota adjuster (auto-bump on usage trends)

GCP offers a quota adjuster that watches usage and requests increases before you hit a ceiling; see the [quota adjuster docs](https://cloud.google.com/docs/quotas/quota-adjuster). It isn't enabled or managed in Terraform today. Worth considering for `INSTANCES`, `SSD-TOTAL-GB` and `N2_CPUS` if usage starts trending upward. It avoids the "burst → blocked → request → wait" loop.
