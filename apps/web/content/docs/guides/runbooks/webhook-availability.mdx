## Symptom

Email from "RunnerForge Alerts": **Availability SLO fast burn (10x over 1h)**, severity CRITICAL.

The availability SLO (99.5% per calendar month, `observability_slos.tf`) counts any 5xx from the
`runnerforge-orchestrator` Cloud Run service as bad. The alert fires when the burn rate over the last hour is
above 10, which means roughly more than 5% of requests in that hour were 5xx. At that rate a month's error budget
is gone in about 3 days. It auto-closes 30 minutes after the condition clears.

## Impact

- A 5xx on `/webhook` is a failed GitHub delivery, and GitHub does not redeliver it on its own.
  - `queued`: no VM is created, so the job stays queued.
  - `completed`: the VM isn't deleted. GCE deletes it once it hits its 6 h 15 min runtime cap
    (`MAX_VM_RUN_DURATION`), or the daily sweep does.
- The SLO covers every route, so a failing `/sweep` (once a day) also counts.

## Diagnose

All commands are read-only.

**1. Confirm the 5xx and which path.** Cloud Run's request log records every response, including ones our access
log misses:

```bash
gcloud logging read '
  logName="projects/runnerforge/logs/run.googleapis.com%2Frequests"
  resource.labels.service_name="runnerforge-orchestrator"
  httpRequest.status>=500
' --project=runnerforge --freshness=2h --limit=50 \
  --format='table(timestamp, httpRequest.status, httpRequest.requestUrl, resource.labels.revision_name)'
```

**2. Find the exception.** Unhandled errors are logged by uvicorn, not by our middleware:

```bash
gcloud logging read '
  resource.type="cloud_run_revision"
  resource.labels.service_name="runnerforge-orchestrator"
  severity>=ERROR
' --project=runnerforge --freshness=2h --limit=20 \
  --format='value(timestamp, jsonPayload.message, jsonPayload.exception)'
```

Match the traceback to a cause:

| What you see | Cause |
|---|---|
| `httpx.HTTPStatusError` from `get_installation_token` or `get_registration_token` | GitHub API call failed. Network errors and 5xx get up to 3 attempts in total (`github_client.py`); 4xx are not retried. A 401 points at the App private key or App ID. |
| `RuntimeError: workflow_job payload did not match the expected WorkflowJob schema`, preceded by ERROR lines like `    - <field>: <msg> (got: ...)` | GitHub changed the payload, or a field we require is missing (`models.py`). |
| A `google.api_core` exception from `create_vm` or `delete_vm` | GCE API rejected the call synchronously (permissions, quota, invalid request). |
| `Sweep failed for VM` lines, or a traceback from `list_runnerforge_vms` | `/sweep` problem. Per-VM failures don't 5xx; a listing failure does. |
| 5xx in the request log but no matching ERROR line | Cloud Run itself: the instance failed to start or crashed. Check the revision's logs around startup. |

**3. Correlate with a deploy.** Check which revision serves traffic and when it was created:

```bash
gcloud run services describe runnerforge-orchestrator --region=europe-west4 --project=runnerforge \
  --format='yaml(status.traffic)'
gcloud run revisions list --service=runnerforge-orchestrator --region=europe-west4 --project=runnerforge
```

**4. Check upstream status:** GitHub at githubstatus.com, GCP at status.cloud.google.com.

## Mitigate

<Callout type="warn" title="Mutations">
  Everything in this section changes production. Each item says how.
</Callout>

- **Bad release:** roll back with the **Deploy Orchestrator** workflow (`deploy-orchestrator.yaml`) via
  `workflow_dispatch`, `action=rollback`, `target=<previous revision name>`. It moves 100% of traffic to that
  revision after approval.
- **GitHub outage:** wait it out. Nothing to change on our side.
- **GitHub auth failures (401 from GitHub):** check that the latest version of the `github-app-private-key` secret
  matches a key that is active on the GitHub App, and that `github_app_id` in Terraform is right.
- **Payload schema drift:** needs a code fix in `models.py` and a release.
- **Recover lost deliveries:** in the GitHub App settings, Advanced, Recent Deliveries, redeliver the failed
  `workflow_job` deliveries once the cause is fixed. A redelivered `queued` creates a VM; a redelivered `completed`
  deletes one.
- **Known, tolerated cause** (for example a GitHub outage): snooze the alert in Cloud Monitoring, Alerting, with a
  reason and an end time.

## Escalate

- GitHub-side failures: GitHub Support, with delivery IDs from Recent Deliveries.
- GCP-side failures (Cloud Run or GCE errors with no code change): GCP support case, with revision name and
  timestamps.
- If rollback doesn't stop the burn, the cause isn't the release. Keep investigating with step 2 and track it in a
  GitHub issue.
