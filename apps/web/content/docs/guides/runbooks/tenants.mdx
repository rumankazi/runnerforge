Installing the GitHub App registers the installation as `pending` in the tenant registry
([ADR-019](/docs/design/decisions#tenant-registry-install-to-register-admin-approval-per-installation-limits)).
Only the owner decides what happens next, with `runnerforge-admin`. It runs on the owner's machine with their own
gcloud credentials: no service account, workflow or release is involved.

<Callout type="info" title="Approvals admit">
  Production admits by the tenant registry (`ADMISSION=registry`). An approved installation gets VMs within its
  limits; any other installation's jobs are rejected (`Installation not admitted` in the orchestrator's logs, with
  the reason). Installations in `ALLOWED_INSTALLATION_IDS` (the owner's) are admitted unlimited without a registry
  read. A self-hosted install without a registry keeps the default, `ADMISSION=allowlist`, and ignores approvals.
</Callout>

## Setup

Once per machine, from `apps/orchestrator/`:

```bash
gcloud auth application-default login
```

```bash
uv run runnerforge-admin list
```

The command bills Firestore calls to the registry's project, and prints which registry it uses
(`projects/runnerforge/databases/runnerforge` by default; `--project` and `--database` change it). Your account
needs read and write access to that Firestore database; the project owner role has it.

## Commands

| Command | Does |
|---|---|
| `list [--state pending]` | Every row: account, `state`, GitHub's status, first approval, limits |
| `approve <id> [--unlimited]` | `state: approved`. A row with no limits gets the beta defaults; one with limits keeps them |
| `suspend <id>` | `state: suspended`: no new VMs, and its deferred jobs are rejected instead of started. Running VMs end with their job or runtime cap; idle ones are deleted by the reconciler's orphan cleanup |
| `set-limits <id> …` | Change limits. Ones not named stay as they are; `--unlimited` or `--defaults` replace all of them |

`set-limits` options: `--max-concurrent-vms N` (1–30), `--max-size small|medium|large|xlarge`,
`--spot-only`/`--no-spot-only`, `--max-runtime-minutes N` (1–360),
`--literal-machine-types`/`--no-literal-machine-types`.

Every write shows the account and the change, then asks before writing; `--yes` skips the question. The
orchestrator picks a change up within a minute (its registry cache).

The command refuses:
- an installation with no row. Rows are created by the `installation` webhook, or by the reconciler's backfill
  in the first 5 minutes of each hour;
- approving or limiting an uninstalled installation (`github_status: deleted`). A reinstall gets a new
  installation ID and registers as `pending`;
- approving a row whose stored limits are invalid, until `set-limits --defaults` or `--unlimited` replaces them;
- a write when the row changed after it was read (for example, a webhook landed while you were answering). Run
  the command again.

Approving an installation that GitHub has suspended works, with a warning: it is admitted only once GitHub
unsuspends it.

A suspension or uninstall on GitHub's side (by the tenant) is handled by the reconciler, not by you: it confirms the
status with GitHub, deletes the installation's VMs, pauses its records while suspended, and deletes them after an
uninstall ([Cut-off installations](/docs/design/webhook-flow#cut-off-installations)).

## Approve a new tenant

1. Find it: `uv run runnerforge-admin list --state pending`. Check the account against the access request.
2. Approve it: `uv run runnerforge-admin approve <id>`. The beta defaults are 2 concurrent VMs, up to `medium`,
   Spot only, 60 minutes per job (a VM cap of 1 h 15 min) and no literal machine types. A job over the VM limit is
   deferred, and the reconciler starts it when a slot frees; a job above `max_size` is rejected (`limit_size`).
3. Check the row: `uv run runnerforge-admin list --state approved`.

## What gets recorded

The command writes `state`, `approved_at`, `limits`, `history` and `updated_at`. The orchestrator creates rows as
`pending` and never changes `state`, `approved_at`, `limits` or `history` after that; it also writes `updated_at`,
on every change of GitHub's status, so the time of your last decision is the newest `history` entry. `approved_at`
is set on the first approval and never cleared. `history` keeps the last 20 decisions (time, action, state,
limits) and expires with the row, 30 days after an uninstall. It doesn't record who made a change, and Firestore
Data Access audit logs are off, so nothing does.
