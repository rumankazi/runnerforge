---
title: Terraform Drift Detected
description: The daily drift check found differences between the Terraform code and GCP.
---

## Symptom

The tfaction drift issue for `infra/terraform` or `infra/terraform-pool` (one issue per target) is reopened, with a comment from the `drift-detection.yaml` run that holds the plan result between current GCP state and the TF code on `main`. The issue itself is created by `create-drift-issues.yaml`; drift detection reopens it when the plan shows changes and closes it when the plan is clean.

## What this means

Drift = a difference between what the TF code declares and what's actually deployed. Common causes:

- A console / gcloud change made outside the TF pipeline
- An out-of-band script that modified GCP resources
- An aborted apply that left state partially updated

Drift isn't necessarily harmful — it means "TF is no longer the source of truth" until reconciled. The drift issue stays open until a later run (scheduled daily at 08:17 UTC) detects no changes, then it auto-closes.

## First step — identify what drifted

Open the issue's latest comment. The plan shows `~`, `+`, `-` markers for resources with changes. Examples to expect:

| Diff | Likely cause |
|---|---|
| `~ google_cloud_run_v2_service.orchestrator` with field-level changes | Someone changed Cloud Run via console (env vars, scaling, etc.) |
| `+` on a resource the code declares | It was deleted out-of-band; the next apply would recreate it |
| `-/+` (replace) | A changed field forces replacement; read the `# forces replacement` line before applying |
| `+ google_project_iam_member_remove.*` | A grant removed in ADR-020 step 3b (pool) or 3f (control) is back, made by hand. Remove it by hand now with `gcloud projects remove-iam-policy-binding <project> --member=<member> --role=<role> --condition=None`, then find out who added it (in the pool, [Pool audit alerts](/docs/guides/runbooks/pool-audit); in the control project, its Admin Activity log for `SetIamPolicy`). An apply removes it only if its PR was planned after the grant came back |

Runner VMs never show up here: the orchestrator creates them through the GCE API, and Terraform doesn't manage them.

## Recovery — two paths

### Path A — Accept the drift (codify in TF)

If the change was intentional and should be kept:

1. Look at the plan in the drift issue's latest comment
2. Edit the TF code in a feature branch to match the deployed state
3. PR the change. Plan-on-PR should show "no changes" if your TF code now matches reality.
4. Merge. `deploy-infra.yaml` will apply (no-op, since state matches code).
5. Next drift run sees clean state → issue auto-closes.

### Path B — Revert the console change

If the change was unintended:

1. Manually revert via console / gcloud / API to match the TF declaration
2. Verify with `gcloud` that the resource matches what's in the `.tf` file
3. Next drift run sees clean state → issue auto-closes.

## Plan lacks a permission

`ci-terraform-plan` reads each project through one custom role only (ADR-020 steps 3 and 3f):

| Target | Role | Codify in |
|---|---|---|
| `infra/terraform` | `controlTerraformReader` in `runnerforge` | `infra/terraform/terraform_ci.tf`, and `control_reader_permissions` and `control_reader_coverage` in `infra/policies/control_reader.rego` |
| `infra/terraform-pool` | `poolTerraformReader` in `runnerforge-pool` | `infra/terraform-pool/iam.tf`, and `pool_reader_permissions` and `pool_reader_coverage` in `infra/policies/pool_reader.rego` |

If a plan or drift run fails with a 403 naming a permission, add that permission to the role by hand (you hold owner):

```bash
gcloud iam roles update <role> --project=<project> --add-permissions=<permission>
```

Then open a PR adding it to the role, to the policy's permission list, and to the coverage entry of the resource type whose refresh failed, so conftest fails if a later PR drops it. Merge it before any other change to that target: an apply planned after your hand change removes the permission again.

A pool plan that stalls for about 5 minutes on `google_monitoring_monitored_project.control_scope` and then fails with a 403 lacks a permission in the **control** project: the pool reads the control project's metrics scope with `resourcemanager.projects.get` from `controlTerraformReader`.

Never add `compute.instances.*`, `compute.disks.*`, log-entry, Firestore-document, secret-version or object reads; conftest rejects them. Don't re-grant `roles/viewer` or `roles/iam.securityReviewer` instead: both list VMs, whose metadata holds runner registration tokens. If one comes back, drift shows `+ google_project_iam_member_remove.*`, but only an apply whose PR was planned after the re-grant removes it, so remove it by hand at once (see the table above). Conftest fails any plan that would grant them.

## Default compute account enabled

A plan, apply or drift run fails with "The control project's default compute service account is enabled" or "The pool's default compute service account is enabled". Both accounts must stay disabled ([ADR-020](/docs/design/decisions#hosted-isolation-a-pool-project-for-tenant-vms)): the control one is an editor, so its token can act as `ci-terraform-apply`. Nothing should run as either. Disable it again (you hold owner):

```bash
gcloud iam service-accounts disable <project-number>-compute@developer.gserviceaccount.com --project=<project>
```

The control project is `runnerforge` (number 8547588670), the pool `runnerforge-pool` (355964341703). Then find out who enabled it:

```bash
gcloud logging read 'LOG_ID("cloudaudit.googleapis.com/activity") AND protoPayload.methodName:"EnableServiceAccount"' --project=<project> --freshness=7d --format='table(timestamp,protoPayload.authenticationInfo.principalEmail,protoPayload.resourceName)'
```

If it was enabled on purpose because something needs it, give that thing its own service account instead. To roll step 3e back, merge a PR deleting `infra/terraform/default_service_account.tf` before you re-enable the control account.

## Manual re-check (don't wait for the cron)

To verify the fix without waiting until 08:17 UTC tomorrow:

```
GitHub Actions → Drift Detection → workflow_dispatch → Run workflow
```

If clean, `update-drift-issue` closes the issue automatically. `tfaction-root.yaml` sets `minimum_detection_interval: 1`, so tfaction skips an issue that was checked less than an hour ago: wait an hour after the last run before dispatching.

## When NOT to act

If the diff shows fields KNOWN to be managed out-of-band (e.g., `client`, `client_version` on Cloud Run — set by gcloud during deploy, in our `ignore_changes` block), they shouldn't be appearing as drift. If they are, it's a bug in the `lifecycle.ignore_changes` config — fix that rather than the apparent drift.
